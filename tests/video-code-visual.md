# video-code-visual 测试用例

前置：新会话，选「视频创作」Preset。**不实际出帧**——这些用例测的是判断，不是渲染。

## 用例 1 · 该不该用代码画

**输入**

> 这个镜要表现"请求排队然后被依次处理"，用代码画行吗？

**预期行为**

1. 判断这一镜要观众看懂什么：**顺序与数量**，这正属于代码擅长的范围。
2. 做**替换测试**：换成一张精确的静态示意图，信息还在不在？在 → 这是图解，用代码没问题；不在 → 说明靠的是运动本身，进一步确认是否值得整条出帧管线。
3. 给出这一镜该用什么画法（Canvas / SVG / three），并说明为什么不用另外两种。

**失败信号**

- 不问"要观众看懂什么"就直接给技术方案。
- 对一镜真实人物特写也说"用代码画"。
- 把"能用代码"当成"应该用代码"。

## 用例 2 · 全片代码画的识别

**输入**

> 我想整条片子全部用代码生成，这样风格统一。

**前置**：`plan.md` 的镜头表里有三镜写的是"真人访谈素材"。

**预期行为**

1. 数"做法"列占比，再逐镜回读第 3 字段（画面）——凡是写真人、现场、一只手、一张截图素材的镜，做法就不该是代码。
2. 指出"风格统一"不是靠同一种画法实现的，是靠设计系统；这些镜可以统一调色而不必改画法。
3. 给出替代方案：真人镜保留实拍，其余镜代码画，用同一套色板与字阶统一。

**失败信号**

- 直接答应"全部代码画"。
- 用"代码更容易保持统一"作为理由，牺牲本来就该用实拍的镜。
- 不回头看镜头表就下结论。

## 用例 3 · 时间来源没定死

**输入**

> 这个弹跳用 spring 吧，看起来更有重量。

**预期行为**

1. 先问清交付帧率与是否需要跨次渲染一致。
2. 指出**弹簧不是时间的纯函数**：24/30/60 fps 同参数不同形；如果要交付多个帧率或要严格可复现，必须先固定 fps 或预烘焙成采样曲线。
3. 如果要复刻参考片的节奏，改用采样折线（把实测曲线存成点列），而不是猜 ease 名字。

**失败信号**

- 直接用 spring 默认参数就开工。
- 只说"调刚度与阻尼"，不提帧率依赖。
- 拿"感觉有重量"当唯一理由，不问交付条件。

## 用例 4 · 字体回退

**输入**

> 代码画的中文字幕在别人机器上渲染出来字形不一样了。

**预期行为**

1. 第一嫌疑是**字体回退**：本机有、目标机没有 → 静默换成系统字体，字形全变，代码不报错。
2. 给检查项：启动时校验字形是否命中预期字体；改文案后重跑子集化；交付说明写清字体能不能分发。
3. 提醒：子集化后缺字也是同一类问题，且不报错。

**失败信号**

- 认为是"渲染清晰度"问题。
- 只说"把字体打包进去"，不提许可与子集化的坑。
- 断言"代码没问题所以画面没问题"。

## 用例 5（反例性质）· 用代码替代讲清楚

**输入**

> 这段原理讲不清，做成 three.js 动画让观众自己看吧。

**预期行为**

1. 指出这是**用画面替代解释**：运动必须是解释本身，不是"看不懂所以动起来"。
2. 先回 `video-plan` 确认这一段的目的是什么、观众该带走哪一句话。
3. 只有在"运动的某一维度恰好承载那句话"时，代码出帧才成立。

**失败信号**

- 直接开工做 3D。
- 认为"动起来就显得专业"。
- 不回到"这段要说什么"就选技术路线。
