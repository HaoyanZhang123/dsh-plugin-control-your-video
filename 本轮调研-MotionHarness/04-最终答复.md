## 一、它是什么（全部实证）

**本地 Rust 守护进程 + 浏览器 Studio + CLI。**

核心契约（Standard）只有两个方法：

```js
export default function ({ root, width, height, pixelRatio }) {
  return {
    prepareFrame(time) { ... },   // time = 绝对项目秒数
    dispose()          { ... },
  }
}
```

**渲染管线**（runtime README 原文）：
> 「The executable contains the Rust daemon and embeds Studio, Core and transient Builder tooling.
> **CDP uses chromiumoxide.**」
> 「**PNG captures a complete browser frame without FFmpeg. MP4 sends complete PNG frames
> directly to native FFmpeg.**」「The capture source is **8-bit RGBA**.」

**成熟度**：

| 项 | 事实 |
|---|---|
| 版本 | **20 个**（不是 21，`0.0.24` 缺号），6 周 |
| 当前 | `0.1.4`，2026-11-11 |
| 仓库 | npm `repository` 指向的 `VibeMG/vibe-motion-graphics` —— **404，不存在**；组织下唯一公开仓库是 `awesome-vmg`（1 star） |
| 条款 | `/terms` `/privacy` `/legal` `/eula` **全 404**，无主体全称 |
| 许可 | 14 个版本 Apache-2.0 → 6 个版本 UNLICENSED，**中途收回** |
| 遥测 | 端点硬编码 `api.motionharness.top/v1/events`，**无 opt-out** |

**⚠️ 官网可信度要打很深的折扣**：那套 `tokens 00 · d_model 4096 / experts 0/32 · top-2 / layers 00/10`
是**纯装饰**，源码级实证——三个数字全部由同一个滚动时间轴 `e` 乘不同缓动窗口得出，必然同增同减；
`d_model 4096`、`top-2`、`/32`、`/10` 是**模板字面量**；`frame` 用 `e*2.4` = **2.4 fps**。
**无 tokenizer、无权重、零模型请求。**

**结论：一切以 CLI 实测为准，官网文案不可信。**

## 三、最锐利的一条：Standard / Pro 是个硬二选一

这是 MH8 挖出来的，我认为**它比任何性能或架构论点都更能定性**。

| | **Standard** | **Pro** |
|---|---|---|
| 技术栈 | **真·随意**（HTML/CSS/Canvas/SVG/Three/GSAP/任意框架） | **锁死** React 19.2.8 + three 0.180.0 + r3f 9.8.1（精确到补丁号） |
| Studio 可编辑参数 | **没有** | 有 |
| 拖关键帧 / 调曲线 | **没有** | 有 |
| 参数从哪来 | — | **源码里 `field.*` 现声明** |

SDK README 原文：
> 「**Standard** uses a default factory…**without a React dependency**. …
> The component and parameter APIs below **belong to Pro projects**.」

**`standard.d.ts` 的 `StandardSceneContext` 只有 `{root, width, height, pixelRatio, media}`——
没有 Layer、没有 parameter、没有 field。**

**所以：「Agent 随便写」和「人在面板上调」不能同时成立。**

而 `Pro` 的参数面板**不是从成品里提取的，是写代码时顺手声明的**：
> 「Agent 没写 `field.text`，人就在 Studio 里没有那个滑块。」

**它要求生成方在第一次写代码时就预判"人类以后会想改哪几个数"。这是知识问题，不是渲染问题。**

## 四、最扎心的一条：它的默认产出，正是我们要治的那个病

`mh new` 官方脚手架生成的默认示例：

```js
prepareFrame(time) {
  const progress = Math.min(1, time / 0.8)
  title.style.opacity = String(progress)
  title.style.transform = `translateY(${40 * (1 - progress) ** 3}px)`
}
```

**这就是 fade-in + 上浮。** 我们这轮的核心矛盾原话是「引擎只会 fade-in，所以丑」。

**MotionHarness 的默认产出，正是那个东西。**

它的七章全在流程侧，**零效果**。SDK 的 `effects` 是后处理滤镜（blur/glow/grain/vignette…），
不是动效设计。**它一个"怎么拍好看"都没有。**

## 五、复用粒度之争（这是决定性的）

| 维度 | **637 张卡** | **MotionHarness** |
|---|---|---|
| 参数来源 | 卡片自带，**2,686 条**（均 4.22 条/张，带 default/range/note） | 源码 `field.*` 现声明 |
| 拿到就能改吗 | **能** | 不能，要先读懂并改 `defineComponent` |
| 复用单位 | **一张卡 = 一个动效** | **一个工程 = 一次生成** |
| 第二次做同类动效 | **换参数** | **重新生成一份代码** |
| 谁承担正确性 | 卡作者（写过 `goodExample`/`badExample`/`avoid`） | 每次生成的 Agent |

> **100 条片子的 100 个相似但不相同的开场：**
> MH 给 100 个 React 工程；637 卡给 1 张卡 + 100 组参数。

**判：真，是倒退。** 不是 React 不好，是**它的复用粒度是"工程"，我们的复用粒度是"动效"**。

## 六、我亲自核实的两条实测

### 6.1 637 张卡的 runtime 分布（完全吻合 MH5 的数字）

```
gsap 213 / svg 128 / webgl 114 / css 103 / canvas 79   = 637
```

### 6.2 ★ 所有演示的动画机制是统一的

我抽样 5 张**有 `index.html`** 的卡（跨 svg / css / gsap 三类）：

```
bar-chart-race(svg)     Motion.timeline=1  Motion.ready=1  CSS动画=0  原生rAF=0
pie-donut-update(svg)   Motion.timeline=1  Motion.ready=1  CSS动画=0  原生rAF=0
flip-reveal(css)        Motion.timeline=1  Motion.ready=1  CSS动画=0  原生rAF=0
orbit-loop(css)         Motion.timeline=1  Motion.ready=1  CSS动画=0  原生rAF=0
source-result-mapping   Motion.timeline=1  Motion.ready=1  CSS动画=0  原生rAF=0
```

**5/5 全走 `Motion.timeline()` + `Motion.ready()`，没有一张用原生 CSS 动画或 rAF。**

**这是个好消息**：标注的 `runtime` 说的是"这个效果本来的技术载体"，
**不是"这个演示怎么跑"**。所以**只要它有你 128 个演示里的 `index.html`，取帧路径就是同一条**，
不需要按 runtime 分支处理。**动作一可以向下修正工期。**

**同时它证实了 MH5 的核心反驳**：卡的 `snippet` 标 gsap，演示却用 `Motion.timeline()`——
**已经是两套写法，中间有一道手工翻译**。再叠一层 React 就是第三层。**纯亏。**

### 6.3 一个必须写进验收的数字

> **动作一的真实交付是「128 个画面 + 509 份配方」，不是「637 种画面」。**
> 637 张里只有 **128** 张有 `index.html`；**509 张只有 `README.md`**。
> 这个数字必须写进验收，否则动作一做完会被判"没兑现"。（MH5）

### 6.4 637 张卡无法批量调参（我自己测的，推翻我的方案前提）

```
accordion-expand    __params=0   数字字面量≈46
annotation-callout  __params=0   数字字面量≈43
answer-stream       __params=0   数字字面量≈21
```

**零个参数注入入口，参数全是写死的字面量。**
所以「卡片能立刻用」与「卡片能调参」是两件事：
- 原样跑 → **零改造**（已验证）
- 可调参 → **每张卡要做一次参数化改造**（128 张）

### 第 1 名为什么是"观察纪律"而不是任何代码

`SKILL.md` 的 `Checks` 节（22 行）原文：

> 「每次用**新的输出目录**」「**把返回的图一起读**」「**只渲染有问题的那一段**」
> 「**帧和电平不证明运动和听感；没看过连播、没听过，就报为未验证**」
> 「**只为具体问题加诊断，不加通用诊断**」
> 「**不要打开、聚焦、seek 或播放用户的 Studio 页面和扬声器，除非被要求**」

对照我们的病：

| 它说的 | 我们的病 |
|---|---|
| 每次用新输出目录 | 接触表覆盖写，看不出变化 |
| 把图一起读 | 只抽 32 帧，没连起来看 |
| 只渲有问题那段 | 每次全片重渲 |
| **没看连播/没听就报未验证** | **验收包恰好写着「未看连续播放、未听音频」** |
| 只为具体问题加诊断 | 建了 27,000 行通用治理 |

**这 22 行是用文档解决的，不是用代码解决的。**
而它划的界线正是你的原则：**可形式化的（纯时间函数、`expectedRevision`）进代码；
需要模型判断的（要看图、要连着看、要听）进纪律。**

## 十一、一句话

**它解决的是「Agent 产出的动效工程怎么被人类编辑和交付」，
我们卡的是「动效本身为什么丑」——这两件事之间没有因果关系。**

买它 = 依赖 +1（163 MB 闭源、无授权、遥测无开关），问题 −0。

**但它的价值不在"它做了什么"，在"它证明了什么是对的"：**
帧契约可以小到两个方法 · 参数必须与源码分离 · 预览与导出必须同一语义 ·
标记必须带语义 target · **「观察」要写成纪律而不是代码**。

**这五条我们都能自己实现，而且已经有一半了。缺的从来不是设计，是接线。**
