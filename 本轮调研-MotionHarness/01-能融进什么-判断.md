# MotionHarness 能融进我们插件的一切｜判断

> 2026-11-11。综合 Lead 一线取证（`00-Lead一线取证.md`）+ 八路并行调研。
> 每条结论都有出处；无法确证的标「未确认」。

---

## 零、先给三条最硬的判断

### 判断一：它的核心不是"动效库"，是**一个帧契约 + 一套工程分层**

```js
// mh.json
{ "projectType": "standard", "entry": "src/scene.js",
  "width": 1920, "height": 1080, "duration": 8, "fps": 30 }

// src/scene.js —— Agent 要写的全部
export default function ({ root, width, height }) {
  const scene = build(root, width, height);
  return {
    prepareFrame(time) { scene.seek(time); },
    dispose()          { scene.destroy(); },
  };
}
```

**两个方法。框架无关**（Three.js / GSAP / Canvas 2D / React 四选一）。

它把"搭预览服务、逐帧导出、音画合成、任意时间定位、工程打包"这五件脏活接走，
让作者只写 `prepareFrame(time)`。

**这恰好是我们 `web-scene` 路线缺的最后一块**：我们已经有 `__seek(sec)` 的取帧思路，
但我们没有"场景契约"这个概念。它给了。

### 判断二：它的许可**分层**，不是一刀切

| 层 | 许可 | 我们能做什么 |
|---|---|---|
| SDK 0.0.11–**0.0.25**（类型/契约层） | **Apache-2.0** ✅ | **读、改、用、分发**（留 NOTICE） |
| CLI 0.0.11–**0.0.25** | **Apache-2.0** ✅ | 同上 |
| SDK/CLI 0.0.26–0.1.4（当前） | UNLICENSED | 只能当外部工具，不能随包 |
| 引擎/Studio/导出器本体 | **从未开源** | 拿不到，只能调用 |

它自己的 NOTICE 原文：
> 「This SDK distribution contains **public document, component and extension type contracts**.
> It does **not** contain the private CLI, editor or engine implementation.」

它自己的 LICENSE 原文：
> 「**Rights already granted for previously distributed versions, including under the
> Apache License, Version 2.0, are unaffected.**」

**所以"融进来"有三种合法形态，且互不冲突：**

| 形态 | 对象 | 许可依据 |
|---|---|---|
| **A. 学设计自己实现** | 数据模型、协作机制、时间语义 | 思想不受版权保护 |
| **B. 直接采用 Apache 版契约** | `TimeMarker` / `EffectSpec` / `MotionState` / `easing` 等类型定义 | Apache-2.0，留 NOTICE |
| **C. 当外部工具调用** | `mh render` / `mh pack` / `mh skill` | 用户自装，不随包 |

**我推荐 A + C，对 B 保持克制。** 理由在第五节。

### 判断三：它解决的**不是我们的主要矛盾**

我们的主要矛盾是：**引擎只会 fade-in，所以丑**。

它的定位是：**给你一套工程外壳，让你用任意技术栈写场景**。
它**不提供**画面内容。它的 README 明说：「SDK 不包含 Builder、Studio、数据引擎或导出 Renderer」。

**换句话说：它替代的是我们"写取帧器 + 打包 + 版本 + 标记"这一段，
不替代我们"做出好看的画面"这一段。**

真正解决"好看"的，仍然是我们手上的 637 张 gongnyang 卡 + 三个 three.js 网页。

## 一、能融进来的清单（按价值排序）

### 第 1 名：`prepareFrame(time)` 场景契约 —— 直接替换我们的 `__seek`

| | gongnyang 的 `stage.js` | MotionHarness |
|---|---|---|
| 接口 | `window.__seek(sec)` 全局函数 | `export default ({root,width,height}) => ({prepareFrame, dispose})` |
| 生命周期 | 无 | `dispose()` 显式释放 |
| 隔离 | 全局变量，多场景会撞 | 模块作用域，天然隔离 |
| 框架 | GSAP 专用 | 任意（含 three.js / Canvas 2D / React） |

**落地**：`web-scene` 对象的 `seekMode` 从 `'seek' | 'clock'` 改成 `'prepare-frame'`，
并把 gongnyang 的 637 张卡**包一层适配器**：
```js
// 适配器：把 stage.js 的 __seek 变成 prepareFrame
export default function ({ root, width, height }) {
  const frame = root.querySelector('iframe').contentWindow
  return {
    prepareFrame(t) { frame.__seek(t) },
    dispose() { root.innerHTML = '' },
  }
}
```
**代价**：约 1 人日。**收益**：场景契约统一，未来接任何技术栈都不用改适配器。

---

### 第 2 名：**三平面工程分层** —— 补上我们 `web-scene` 缺的那一环

```
bg    → assets/          素材原件
actor → src/             源码绘制
fg    → document.json    参数（人调）
```

**机制**（它 UI 的两句提示语就是全部语义）：
- 人调参 → 「手调参数：**源码未改动**」
- Agent 改码 → 「Agent 改源码：**参数保留**」

**为什么这是我们必须学的**：
我们引入 `web-scene` 后，一个场景就是一个 HTML/JS 文件。
**人调的参数存哪？** 如果写回源码：
- Agent 下次改源码会覆盖用户手调 → 用户白调
- 每次调参 git diff 爆炸 → 版本系统失效

**设计建议**（落到我们的 CompositionPlan）：
```
project/
  scenes/
    s1/
      scene.js          ← Agent 写，人只读
      scene.params.json ← 人调，Agent 只读
      assets/           ← 素材原件（哈希锁定）
```
`scene.js` 从 `scene.params.json` 读值；`CompositionPlan` 里只存 `sceneRef` + `paramsRef`。

**代价**：约 2 人日（含冲突判定）。**收益**：这是"编辑"这件事能成立的前提。

---

### 第 3 名：**确定性时间语义** —— 我们 `remap.js` 有实现但没接线的部分

它 `motion.d.ts` 的注释（原文）：

> 「**Stateless motion**…Options describe the complete curve at each evaluation;
> changing them does **not resume a hidden simulation**.」
> 「Seeded 1D smooth value noise; **independent of evaluation order and FPS**.」
> 「**Reconstructs from start on every call: no playback memory or wall-clock delta.**」
> 「Each interval holds its endpoint source value; the last partial interval is evaluated
> independently, so **seek order and output FPS cannot change the curve**.」

**这解决了我上一轮的一个疑虑**：秒制会不会引入浮点漂移？
它的答案：**只要每个采样点都由纯函数从 `t` 重算，秒制与帧制在确定性上等价。**

**它明确划出的"不可 seek"边界也很重要**：
> 「Calculate final state from absolute time; incremental physics, independently created
> clocks and temporal-feedback effects are **not made seekable automatically**.」
> 「R3F clock **does not run on wall time**; delta is zero on first/repeated frame and
> signed elapsed seconds between subsequent draws, **including negative seeks**.」

**落地**：把这段语义写进我们 `CT-04` 契约，作为 `web-scene` 的硬要求：
`prepareFrame(t)` 必须是 `t` 的纯函数；不许内部累加；随机必须种子化。
**代价**：0（只是契约文字）+ 验收用例 1 人日。

---

### 第 4 名：**`TimeMarker` 标记模型** —— 我们 `editing/` 5,389 行可以对照精简

它的真实类型（Apache-2.0）：

| 字段 | 作用 |
|---|---|
| `target` | **四级语义定位**：`instance` / `component` / `timing` / `parameter` |
| `anchor` | 画布像素：点 或 矩形 |
| `timeSpace` | `project` / `source` / `object` 三种时间空间 |
| `requestVersion` | 内核维护的指令版本，**独立于 document revision** |
| `context` | `{ documentRevision, name, componentId, value, field }` |
| `completion` | `{ requestVersion, summary }` |
| `intent` | `delete-instance` / `delete-standard-audio` / `pro-edit` |

它自己写的三句关键注释：
> 「Stable semantic location; **coordinates alone never identify an object**.」
> 「For canvas annotations, time, anchor, annotated screenshot and notes are primary;
> an optionally associated target and its context are hints.」
> 「**Interpretation and animation decisions belong to the Agent.**」

还有一条产品级克制，和我们 `需求共识` 里"未回复不等于确认"是同一种东西：
> 「**完成记录表示 Agent 确认，不代表用户验收。**」

**对照我们**：`editing/annotations.js` + `candidates.js` + `sessions.js` = 5,389 行，且不可达。
它的标记模型**轻得多**，而且是产品化验证过的。

**落地**：不抄代码（Apache 版只有类型，没有实现），**照这个字段设计重写我们的注释模型**。
**代价**：2–3 人日。**收益**：可能砍掉 `editing/` 的一大半。

---

### 第 5 名：**参数契约 `ComponentCommand` 模型** —— 解决"谁能改什么"

它的命令模型（`authoring-types.d.ts`，Apache-2.0）：

```ts
type ComponentCommand =
  | { type: 'edit'; value: EditableValue }
  | { type: 'keyframe/set' | 'keyframe/edit' | 'keyframe/remove' | 'keyframe/loop' }
  | { type: 'timing' }                    // start/duration/offset
  | { type: 'time-remap/stretch' | 'time-remap/retime' | 'time-remap' }
  | { type: 'effects'; operation: 'add'|'remove'|'set'|'keyframe-set'... }
  | { type: 'geometry'; operation: 'set'|'resize'|'anchor'|'unit'|'aspect-lock' }
  | { type: 'table' } | { type: 'sequence' }
  | { type: 'keyframes/selection'; operation: 'paste'|'scale'|'move'|'copy'|'easing'|'remove' }
  | { type: 'stagger' } | { type: 'reset' }
```

注释原文：
> 「**Semantic data operations, validated against the host capability catalogue.
> No filesystem, source, history or rendering operations are accepted here.**」

**这是"把可形式化的操作交给代码"的教科书**：所有编辑都被表达成**语义命令**，
而不是"改这个字段"；而且命令集**故意不包含**文件系统/源码/历史/渲染操作。

**对照我们**：我们的 `editing/field-diff.js`、`guard.js`、`scope.js` 在做类似的事，但
**没有统一的命令模型**——所以"谁能改什么"散落在各处。

**落地**：把我们的编辑操作收敛成 `ComponentCommand` 式的语义命令集。
**代价**：3–5 人日（重构 `editing/`）。**收益**：D1 那类"改属性画面不变"的缺陷从根上不可能发生。

---

### 第 6 名：`Layer offset` 模型 —— 解决"叠加动作 vs 可编辑基础值"

```tsx
<Layer bindings="parameters" value={basicTransformValue(values)}
  offset={{ rotation: values.tilt }}>
```

注释原文：
> 「Numeric parameter edits address **the base**. Canvas gestures use **the displayed pose**
> and subtract the offset captured at gesture start before writing changed base channels.
> With base rotation 10° and offset 3°, dragging the displayed angle to 20° **saves 17°**.」

**这就是"参数与派生值分离"**：基础值可编辑，叠加动作只读，且两者不互相污染。

**落地**：我们的 `web-scene` 参数里区分 `base`（人可调）与 `offset`（代码派生）。
**代价**：1 人日。**收益**：避免"人调完被 Agent 的下一次渲染覆盖"。

---

### 第 7 名：`mh skill` 这个**知识投递机制** —— 直接对应我们上轮的"卡片检索"

它的做法：`mh skill` 输出给 Agent 阅读的 skill 文档；`mh skill --reference audio --section "..."`
支持**分区取用**。
还有 `mh hook install --agent codex|claude-code|kimi-code`：**每条新用户消息自动附带当前待办标记**。

**这正是我们上轮设计的"三闸检索"的产品化版本**：
不是把所有知识塞进上下文，而是**按需拉取指定章节**，并**在正确的时刻自动注入**（hook）。

**落地**：我们的 `cards.search` 工具 + `{ when }` 阶段门，形态上可以更简单：
```
cards.list({ domain })            → 目录
cards.get({ id })                 → 单卡
cards.bySymptom({ text })         → 症状匹配
```
**代价**：已经在计划里（动作三），不用额外做。

### 第 8 名：`EFFECT_DEFINITIONS` 效果目录 —— 一份现成的、字段对齐的效果表

它定义了 18 种效果及其参数范围（Apache-2.0 类型）：
`blur` / `backdrop-blur` / `color-adjust`（brightness/contrast/saturation/hue/grayscale/sepia）/
`shadow` / `inner-shadow` / `glow` / `blend-mode`（16 种混合模式）/
`effect-mask` / `gradient-overlay` / `vignette` / `light` / `grain`（带 seed）/ `texture-overlay` /
`svg-distortion`（带 seed）/ `frame`。

**我们一个都没有**（`blend` 命中 0、`mask` 命中 0）。

**但注意**：这只是**参数定义**，不是实现。要实现得自己在 Web 场景里写。
**而且这些全部是二维 CSS 级效果**——它没有三维镜头。

**落地**：作为我们效果目录的**命名与参数对齐参考**，不直接抄实现。
**代价**：0（参考）。**收益**：效果库设计有依据。

## 二、不能融 / 不该融的

| 项 | 为什么 |
|---|---|
| **它的引擎/Studio/导出器** | 从未开源，UNLICENSED，只能当外部工具 |
| **它的 `mh open` Studio** | 是 macOS/Windows GUI 应用，我们的 UI 是自己的，两套会打架 |
| **达芬奇桥接** | 仅 macOS，我们是 Windows；而且我们不需要"剪片"，需要"出片" |
| **它的 React + R3F 全套** | 引入会带来 `react` / `react-dom` / `@react-three/fiber` / `three` 一条依赖链，与我们"薄插件"矛盾 |
| **它的匿名埋点** | CLI README 明说"默认收集匿名使用事件…命令与运行结果、Studio 点击、按键、版本、系统信息、**以及可识别的编程 Agent**"。**这是隐私问题**，必须在插件里显式告知或禁用 |
| **官网那套 `mh.layer()` DSL** | 是打字机装饰代码，不是真 API（已实证） |

## 三、它的产品判断里，有几条比技术更值钱

1. **「完成记录表示 Agent 确认，不代表用户验收」** —— 和我们的"未回复不等于确认"同源。
2. **「Interpretation and animation decisions belong to the Agent」** —— 明确把创作决策交给模型。
3. **「coordinates alone never identify an object」** —— 坐标不能当身份，必须有语义 target。
4. **「No filesystem, source, history or rendering operations are accepted here」** —— 命令集故意窄。
5. **「增量物理、独立时钟、时间反馈效果不会被自动变成可 seek」** —— 诚实地划出能力边界，而不是假装都能。

**这五条，我们文档里一条都没有。** 它们不是代码，是**判断力**。

## 四、如果只做一件事

**做"三平面工程分层 + `prepareFrame` 契约"这一件。**

理由：
- 它同时解决了我们引入 `web-scene` 后**最迫切的三个问题**：
  ① 场景用什么接口（`prepareFrame`）
  ② 人调的参数存哪（`document.json` 层）
  ③ Agent 改代码会不会覆盖人调（不会，因为隔离）
- 它是**我们上一轮"动作一"的必要补全**，不是额外工作
- 它**不依赖它的任何代码**，纯设计借鉴，零许可风险

**代价估计：3–4 人日**（契约 1 + 分层 2 + 适配器 1）。
**收益**：`web-scene` 从"一个想法"变成"一个可被人调、可被 Agent 改、可被确定重现的工程"。

## 五、要不要直接采用 Apache 版 SDK？

**我的建议：读它、对标它、但不引入它。**

| 论点 | 支持引入 | 反对引入 |
|---|---|---|
| 许可 | Apache-2.0 可分发 | 只有类型层，没有实现，引入也只能拿到 `.d.ts` |
| 依赖 | peer 是 three/react/r3f，可选 | 要引入就是一条 React 生态链，与"薄插件"矛盾 |
| 版本 | 0.0.25 已停更（当前 0.1.4 是 UNLICENSED） | **采用一个已停更的分支会立刻落后** |
| 覆盖 | 类型定义确实完整 | 我们的 `CompositionPlan` 已经是自己的模型，引入等于两套并存 |
| 价值 | 可以少设计一些类型 | **读一遍就能学到的设计，不值得引一条依赖** |

**一句话**：它的类型定义是**极好的教科书**，但不是**该引的依赖**。

## 六、一个必须提醒的风险

CLI README 原文：
> 「The public CLI collects anonymous usage events by default: command and run outcomes,
> Studio control clicks and keys outside text editors, versions, system details,
> and **the coding agent when identifiable**. An installation uses a random local ID.
> Source code, projects, assets, paths, command arguments, and typed text are not uploaded.」

**它默认上报，包括"可识别的编程 Agent"。**
如果我们把 `mh` 当外部工具调用，**用户需要知道这件事**，且应该有开关（它提供 `MH_NO_UPDATE_NOTIFIER` 等，
但埋点本身的关闭方式未在 README 中明确，**未确认**）。

**这条写进我们的工具接入说明，不能默默带过。**

### 还有一条更难看的：它没有条款

`/terms` `/privacy` `/legal` `/eula` **全部 404**；站点 bundle 全文检索
`Terms`/`Privacy`/`license`/`价格`/`商用`/`水印` **全部 0 命中**；
页脚只有 `浙ICP备2026009289号-2` + `© 2026 MOTION HARNESS`，**连经营主体全称都没有**。

含义：
- 「用它出的片能不能发 B 站」**没有合同答案**，只有著作权默认规则
- 拿不到发票，也**找不到人签授权书**
- `STANDARD` / `PRO` 是**功能门**（PRO = 界面编辑 / 代码参数隔离 / 达芬奇桥接），
  **不是许可档位**；哪一档能商用、输出归谁、有无水印，**公开渠道一个字都没有**

### 三条红线（建议直接写进规约）

1. `package.json` 的 `dependencies` / `devDependencies` 里**永不出现** `@motionharness/*`。
   需要探测就 `spawn` / `which`，不 `import`。
2. 仓库里**永不出现**它的二进制、`.vmg`、模板、Logo、示例动画、界面截图
   （截图只进调研文档，不进包）。
3. 内部文档与代码里，**不出现**它的私有格式解析器。适配层只认「命令 + 输出文件路径」，
   不认内部结构。

### 路径 B 的法律依据（这条最重要，因为它让我们可以放心学）

《计算机软件保护条例》：
- **第十七条**：「为了学习和研究软件内含的**设计思想和原理**，通过安装、显示、传输或者
  存储软件等方式使用软件的，**可以不经软件著作权人许可，不向其支付报酬**。」
- **第六条**：「本条例对软件著作权的保护**不延及**开发软件所用的**思想、处理过程、
  操作方法或者数学概念**等。」

**所以：照它的数据模型、协作机制、时间语义自己重写，是合法的。**
守三条即可：**只看行为不看代码、不逐像素复刻 UI、不照抄界面文案与字符串。**

### 一条必须承认的代价

路径 A 的「干净」建立在「MH 侧无权可依」之上。这不是我们造成的风险，
但风险确实由使用它的用户承担。所以产品文案必须写清：

> 「MotionHarness 是其权利人所有的专有软件，需用户自行安装并遵守其条款，
> 本插件不随附、不分发、不提供其授权。」

这句话既是免责，也是「薄插件」定位的自证。
