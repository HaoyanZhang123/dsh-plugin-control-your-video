# 范式：不做工作台，做一套「会看片子的手艺」

> 2026-11-12。这份文档回答一个问题：一个人 + 一个 Agent，怎么做视频。
> 不是架构，是**可执行的东西**：一个 190 行的渲染器 + 一组 SKILL.md。

---

## 零、先承认三件事

### 1. 你的沮丧是准确的

你做了 53,783 行生产代码、15,973 行测试、27,000 行治理、12 份规划文档、70 个资产目录的审计。

**这些一行都不能出片。**

而一个 190 行的 `render.mjs` 在今天跑出了第一条片子：4 秒、120 帧、h264、sha256 可复现、37.8 秒完成。

**这不说明你愚蠢。说明你把"让作品正确"和"让工程正确"搞混了。** 后者你做到了，前者你还没开始。

### 2. 但那些工作不是白费

你已经拿到的、不可替代的认知：

| 资产 | 价值 |
|---|---|
| **D1–D4 四条实测缺陷** | `fit`/`box` 被忽略、文字晚 122 帧、xfade 截短 52%、`rgba()` 抛错。**这四条是"引擎表达力不足"的铁证**，任何后来者都要重踩 |
| **637 张卡的实测画像** | 128 张有 `index.html`、509 张只有 README；`__params` 全 0；`Motion.timeline` 统一 |
| **`__seek` 确定性验证** | 同帧 sha 一致、跨进程一致、11.5 ms/帧 |
| **314 MB 素材的分类与许可裁定** | 70 目录四档、AGPL/Apache 边界、`unknown` 579 处 |
| **MotionHarness 的完整拆解** | 12 份文档，包括它的 Standard/Pro 二选一、`.vmg` 断代、隐藏遥测 |

**这些是知识，不是代码。它们该住在 SKILL.md 和 references 里，不该长出 5 万个函数。**

### 3. "重工作台 + 聊天框"为什么必然失败

不是因为它老土，是因为它**违反了一条信息经济学**：

> 一个界面占的是**用户和模型之间唯一的带宽**。
> 如果你把一个决定做成"点按钮 → 写数据库 → 渲染 → 读回 → 显示"，
> 你就把一次对话变成了六次交互，每一次都要人等。

而视频创作的真实节奏是：**看一眼 → 说一句 → 再看一眼**。
你要的是把这个环压到 5 分钟以内，不是把环画进 ER 图。

## 一、`control-your-skills` 到底教会了什么

我把它四个 skill 全读了。它值得学的不是"它做了什么"，是**它几乎什么都没做**：

```
四个 skill = 四个 SKILL.md + 三个 references + 一个校验脚本
零构建、零依赖、零数据库、零 UI
安装方式：一个 junction 链接
```

而它解决的是真问题（Git 发版纪律、仓库呈现、论文配图去 AI 味）。

### 1.1 三层渐进披露

| 层 | 内容 | 何时进上下文 |
|---|---|---|
| 1 | `name` + `description` | **常驻**（catalog 只显示这两个） |
| 2 | `SKILL.md` 正文 | **触发时** |
| 3 | `references/` / `scripts/` / `assets/` | **按需**，脚本可执行而不读入 |

**关键洞察**：`description` 是唯一的触发面。正文加载时，触发决定已经做完了。
所以「何时使用本 skill」**不能写在正文里**，必须写进 `description`。

### 1.2 自由度分级（这条最该抄）

`skill-creator` 原文：

> **窄桥装护栏，旷野给方向。**

| 自由度 | 形态 | 用在哪 |
|---|---|---|
| **高** | 散文式原则 | 多种做法都成立、依赖上下文判断 |
| **中** | 带参数的脚本 / 伪代码 | 有惯用做法，允许变体 |
| **低** | 固定脚本、几乎无参数 | 操作易错、必须每次完全一致 |

**这才是你说的那句话的可操作版本。**
不是"决策给模型、操作给代码"这种二分——而是**按任务的脆弱程度给不同强度的约束**。

### 1.3 三条判死标准（`skill-creator` §0）

**不该做成 skill**：
- 一次性的小任务
- 模型本来就会的通用知识
- 需要确定性计算或联网的动作（写脚本，让 skill 调用它）

以及那句最狠的：

> 一个 skill 被加载，占的是**和其他所有上下文共享的窗口**。
> 它必须能回答：**"这段话是模型本来不知道的吗？"**

**用这条尺子量我们那 27,000 行治理：**
锁、原子写、版本、恢复、"未回复不等于确认"——**模型全都会**。它不需要你教。
它不会的是：**这 637 张卡里哪一张适合这个镜头、这个转场在这里是加分还是偷懒、这条片子的第二秒观众会不会划走。**

## 二、范式：三层，各管各的

```
┌────────────────────────────────────────────────────────────┐
│ ③ 手艺层（SKILL.md）                                        │
│    模型读它，知道"该怎么想、该怎么看、什么时候停手"          │
│    例：怎么选镜头、怎么判断一条片子能不能发、怎么看接触表    │
├────────────────────────────────────────────────────────────┤
│ ② 工具层（scripts/）                                        │
│    模型调用它，做确定性的事：渲染、探测、拼接、量规格        │
│    例：render.mjs（190 行）、join.mjs、probe.mjs            │
├────────────────────────────────────────────────────────────┤
│ ① 素材层（assets/ 与外部目录）                              │
│    637 张卡、三个 three.js 网页、用户的素材                 │
│    模型检索它，按需取用                                     │
└────────────────────────────────────────────────────────────┘
```

**没有第四层。没有数据库、没有时间线模型、没有 UI。**

### 2.1 为什么这能成立

因为你只有一个人、一条片子、几个素材。

- **时间线**：一条 30 秒的片子就是 5–8 个镜头，用一份 `plan.json` 或几句 ffmpeg 命令就够
- **版本**：git 就是版本系统，不需要你重写
- **锁**：你一个人，不会和自己冲突
- **恢复**：文件还在就是没丢

**这些不是"不重要的工程"，是"已经被别人解决了的工程"。** 重写它们，是在给自己造一个更难维护的 git。

### 2.2 每一层由谁驱动

| 层 | 谁写 | 谁读 | 变更频率 |
|---|---|---|---|
| 手艺 | 你（一次性，然后迭代） | 模型 | 低 |
| 工具 | 模型（一次，然后固化） | 模型调用 | 低 |
| 素材 | 你 + 外部 | 模型检索 | 高 |

**注意工具层是"模型写"**——这就是 190 行 `render.mjs` 的来历。模型需要什么，它自己写；
写好了就固化进 `scripts/`，从此不必重写。**这是"把可形式化的交给代码"的正确时序：不是先设计好再写，是用到了才写。**

## 三、实做：四个 skill

### 3.1 `film-render` —— 把场景渲成片子

**自由度：低。** 固定脚本，几乎无参数。

```
film-render/
├─ SKILL.md
├─ scripts/render.mjs      190 行（已跑通）
└─ references/scene-protocol.md
```

**它只做四件事**：注入时间、逐帧取像素、按真实帧率编码、读回规格 + 出接触表。

**场景协议**（已实测三种）：
| 接口 | 来源 | 状态 |
|---|---|---|
| `window.__seek(t)` | gongnyang 637 张卡 | ✅ 实测通过 |
| `window.__YOI__.setTime(t)` | 花园.html | 待测 |
| 时钟注入 `__pump()` | 无接口的页面 | 已实现，未验证 |

**已完成实测**：
```
ken-burns 4s@30fps → 120 帧 / 4.000s / 314,947 B / sha256 cb7f5f99…
逐帧哈希：120 帧中 117 帧互不相同
两张卡 + xfade → 165 帧 / 5.500s / 365 KB，转场在接触表第 6 格可见
```

**这个 skill 的 `description` 要写成**（三段：做什么/何时用/不适用）：
> 把一个可 seek 的 Web 场景渲成视频文件。当需要把 HTML/Canvas/Three.js/GSAP 场景变成 mp4，或需要一条片子的真实帧数、时长、帧率、逐帧差异时使用。不负责场景怎么写（那是创作），不负责多镜头编排与音轨（用 film-cut）。

### 3.2 `film-look` —— 怎么看一条片子

**自由度：高。** 散文式判断，因为审美不可形式化。

```
film-look/
├─ SKILL.md
└─ references/
   ├─ contact-sheet.md    怎么看接触表
   ├─ motion-proof.md     怎么证明"在动"
   ├─ rhythm.md           怎么看节奏
   └─ dead-frame.md       怎么找废帧
```

**这是整个方案里最重要的一块，因为它是我们过去半年最缺的那一环。**

内容骨架（照 `SKILL.md` 的 Checks 结构写，不抄文字）：

> **看之前**：每次用新的输出目录，不要覆盖上一次。
> **看什么**：接触表要**连起来看**，不是只看一格。
> **证明运动**：接触表不证明运动。要 `ffmpeg -f framemd5` 数唯一帧。
> **只渲有问题的那段**：不要全片重渲。
> **没看连播就说没看**：没听过音频就说没听。不要用"帧率对、电平正常"冒充"好看"。
> **只为一个具体问题加诊断**，不要加通用诊断。

**判据（写进 skill，不是写进代码）**：
- 抽任意一帧脱离上下文，它还像一张海报吗？
- 关掉字幕，还知道在讲什么吗？
- 关掉声音，节奏还在吗？
- 从第 1 秒到第 30 秒，有没有超过 3 秒什么都没发生？

### 3.3 `film-cut` —— 把镜头拼成一条

**自由度：中。** 带参数的脚本。

```
film-cut/
├─ SKILL.md
├─ scripts/cut.mjs        （待写，约 120 行）
└─ references/transitions.md
```

**职责**：读一份极简 `plan.json`，调 `film-render` 出各段，按转场拼接，叠音轨，出终版。

`plan.json` 就长这样（**没有 CompositionPlan，就这么简单**）：
```json
{
  "fps": 30,
  "size": [1920, 1080],
  "shots": [
    { "scene": "scenes/opening.html", "seconds": 4 },
    { "scene": "cards/ken-burns/index.html", "seconds": 3, "params": { "zoom": 1.2 } },
    { "scene": "scenes/garden.html", "seconds": 6 }
  ],
  "transitions": [ { "kind": "fade", "seconds": 0.5 }, { "kind": "wipe", "seconds": 0.4 } ],
  "audio": { "file": "audio/bed.wav", "gainDb": -18 }
}
```

**注意：`transitions` 用 `xfade` 的名字表**——`fade`/`wipeleft`/`circleopen`/`pixelize`/`radial`…
**一行代码就能支持 20 多种转场**，这就是我们上一轮查到的"白送的"。

### 3.4 `film-craft` —— 怎么把片子做好看

**自由度：高。** 这是纯判断，也是唯一真正稀缺的东西。

```
film-craft/
├─ SKILL.md
├─ references/
│  ├─ camera.md          镜头怎么走（从 22 张 camera 卡提炼）
│  ├─ rhythm.md          节奏怎么排
│  ├─ type.md            字怎么排
│  └─ anti-patterns.md   什么最俗
└─ assets/cards.index.json   637 张卡的检索索引
```

**它不讲"怎么用工具"，它讲"什么样的片子不难看"。**

核心判据（从我们实测的失败里反推）：

| 我们犯过的错 | 对应的手艺 |
|---|---|
| 全片 0 次硬切，一镜到底漂移 | 镜头长度要有变化；说三句话就要切一次 |
| 画面里有鼠标光标 | 素材是录屏就承认，或者重渲 |
| 图层数 10 个但全是 fade-in | 运动要有层级：主运动 + 跟随 + 环境 |
| 三种视觉规则同框（插画+像素+UI卡） | 一条片子只有一个"世界" |
| 声音是噪声+四声咔 | 声音要么有旋律，要么刻意静默，不要填充 |
| 片尾把工程说明烧进画面 | 观众不关心你怎么做的 |

**这一节是整个方案里最难写的，也是最值钱的。** 它不能由我一次写完，只能在真实片子上一轮轮攒。

## 四、一次真实的创作循环长什么样

不是流程图，是**对话记录**。

```
你：做一条 20 秒的片子，讲我这半年做出来的三个世界。
    素材在 已确认资产/.../ 三个网页我放你桌面上。

模型：（读 film-craft，看 anti-patterns）
    先给我三个方向，每个一句话。

你：第二个。

模型：（读 film-craft/camera、rhythm）
    写下 plan.json（4 个镜头 / 3 个转场 / 20 秒）
    调 film-render 出 4 段，调 cut.mjs 拼起来
    出接触表 + framemd5

模型：渲好了，20.1 秒，603 帧。
    但我看接触表发现第 3 个镜头连续 4 秒没有变化 —— 一个静止画面。
    你要吗？还是换一张卡？

你：换。

模型：（改 plan.json 一个字段，重渲那一段）
    时长 19.8 秒。接触表现在每格都有差异。

你：可以。
```

**注意这个循环里没有的东西**：没有工作台、没有项目列表、没有版本对话框、没有"确认按钮"、
没有渲染队列、没有成就系统。**只有一句一句的判断。**

**而它的每一轮都是 30–60 秒，不是小时。**

## 五、为什么这回不会重蹈覆辙

你上一次失控，有一个可识别的拐点：**当你开始为"以后可能会有的需求"写代码时。**

- 跨画幅适配 → 一个人发 B 站，先做 16:9 就够
- 项目包往返 → 没有第二个人会打开你的工程
- 候选/对照/批注 → 一句话 + 一个对比帧就够了
- 生产锁/单写入者 → 你一个人
- 63 个测试 → 190 行脚本要 63 个测试吗

**约束（写死，不许破）：**

1. **一个 skill 不超过 150 行 SKILL.md**（`skill-creator` 的硬规）
2. **一个 script 不超过 300 行**。超了说明你在造框架。
3. **不引入依赖**。Chrome + FFmpeg + Node 内置模块，够用。
4. **不写 UI**。DSH 就是 UI。
5. **不建数据库**。文件 + git。
6. **没有"以后可能会用"**。用到了才写。

**如果某天你想加第 7 条约束，先问：这条约束是给模型的，还是给我的安全感？**

## 六、第一个可验证的里程碑

**不是"插件完成"，是这一件事：**

> **从"我有个想法"到"我看到一条 20 秒的片子"，不超过 10 分钟。**

判据：
- 全程不离开 DSH 对话
- 模型不要求你手动跑任何命令
- 至少经过 2 轮"我说不行 → 它改 → 我再看到"
- 每一轮 ≤ 2 分钟

**现在离这个目标有多远？**

| 已有 | 缺 |
|---|---|
| `render.mjs` 190 行，能出片 | `cut.mjs`（约 120 行） |
| 637 张卡可直接用 | 卡片检索索引 |
| 三个 html 待测 | 场景协议适配 |
| 你知道 D1–D4 是什么 | 4 份 SKILL.md |
| — | **一套能判断"好不好看"的标准**（最难） |

**大约 2–3 天能到"能出片"，2–3 周能到"出得还行"。**

## 七、我不确定的地方

说清楚，不粉饰：

1. **这套范式能不能做出"电影感"** —— 不确定。它很擅长"信息清楚、动效可信、图文漂亮"（637 卡的范围）。
   要"一个活的 3D 世界"，得你自己写 three.js 场景。**两条路不冲突，但第二条更慢。**
2. **模型的审美判断能否稳定** —— 不确定。它可能把"花"当"好"。这需要 `film-look` 的判据写得足够硬，
   而且需要你不断纠。
3. **10 分钟回路是否现实** —— 不确定。取决于你的机器和你对"能看"的容忍度。
4. **你自己会不会又滑回去** —— 这是我最不确定的一条。**写代码的快感远大于看片子的挫败感。**
   这就是为什么要有第五节的六条约束。

## 八、如果你只做一件事

**写下 `film-craft/SKILL.md` 的第一版，哪怕只有 20 行。**

不是写代码，是把你对"什么片子不难看"的判断写下来。

因为你已经有了答案——你在第一条消息里就说了：**「我看了成片，真实感受是：丑。」**
你能看出丑，说明你知道不丑长什么样。

**把它写下来，模型才有东西可学。**

这比再写 5 万行代码有用。
