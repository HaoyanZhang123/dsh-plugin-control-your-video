### 仍然咬合的三对（可接受，不合并）

规范 §8 明确说过：允许自然重叠与组合使用，不为互斥而让用户换措辞。下面三对确实是同一句用户话会同时命中两条，但**先后顺序是明确的**，属于设计上的串联而非撞车：

| 对 | 同一句用户话 | 为什么不算撞车 |
|---|---|---|
| `video-intent` ↔ `video-plan` | "就照这条片子的感觉做" | intent 先拆参考的**层次**（结构／节奏／视觉／具体效果）并写"借什么不借什么"；plan 拿到拆完的结论才排结构。plan 的触发词已改成"参考拆完了，按它排结构"，把原句留给 intent |
| `video-review` ↔ `video-edit` | "压脸了" / "字幕不方便看" | review 的触发词是**提问式**"字幕是不是压脸了"（要取证）；edit 的表格里是**陈述式**"字幕挡住了人/挡住画面"（要改位置）。前一句问事实，后一句下命令 |
| `video-release` ↔ `video-sound` | "响度够不够" | sound 只答**测量读数**（怎么量、量出来是多少）；release 只答**能不能交**（平台目标与容差在哪）。数值只在 sound 侧写一次，目标表只在 release 侧写一次 |

## 四、仍然咬合的判断，留给验证阶段

下面这些不是文档问题，是**只有真跑起来才知道**的事：

1. **intent → plan 的交接是否真的顺**。文档上先后清楚，实际会话里模型会不会跳过 intent 直接出方案，要看测试用例 `video-intent.md` 用例 2 与 `video-plan.md` 用例 3。
2. **motion 会不会仍然抢转场**。它现在只有指针，但"两镜接得硬"这种话同时像节奏问题与动效问题。
3. **sound 会不会顺手改词**。人声路线归它、文本归 script，边界写了，实际会不会越界要跑用例。
4. **review 的"未取证"会不会被跳过**。修改单第 2 项要求带 id 或写"未取证"，这是最容易偷懒的一栏。
5. **release 会不会被当成审批关卡**。它明确写了"自动检查只是证据、不设签字流程"，但"能不能发"这个词本身就会诱导出审批语气。
