# control-your-video 编写规范

状态：2026-11-22（V3）。本文件定义三件事：**Agent 与工具之间必须共用的接口**、**知识与 Skill 的边界**、**数值与来源怎么写**。

**一句话**：接口只有一个定义处；Skill 正文只写判断；细节进参考；每份参考都写清什么条件下读。

本文件**不规定** Skill 的章节结构、行数、示例数量、小节名称。那些由具体内容决定，不由格式决定。一份 40 行说清一种判断的 Skill，比一份 200 行填满六节的 Skill 好。

## 0. 适用范围与优先级

1. **用户当前的明确要求 > 已确认的产品决策 > 本规范。** 本规范管"怎么写"，不管某个作品该做什么。
2. 接口（§1）是与代码的契约，必须遵守；其余各节是判据，遇到具体内容可以按更好的做法处理，并把理由写进那份文件。
3. 接口一律是**人读的 Markdown**，只有一个例外：§1.5 的证据条目由脚本读写，键名不能改。
4. 改接口必须同时改本文件、`tools/` 里的实现与对应测试，并在 `CHANGELOG.md` 记影响面。单份 Skill 不得私自增删字段或改名。

## 1. 与代码耦合的共享接口

这些是**别人会读、脚本会解析**的东西。Skill 正文只用、不复述字段表；要说明时举一两行示例，并写清"定义见 `docs/编写规范.md` §1.x"。

### 1.1 镜头规格（`plan-check` 会解析）

全部镜头都要详细到可执行。**镜头表与逐镜小节两种写法都认**，不必迁就某一种格式。

每一镜至少要能被读出这些东西：

| 要读出的 | 说明 |
|---|---|
| 镜号 | 能排序、能引用；`plan-check` 认 `1`、`01`、`S01`、`镜 1`、`第1镜`、`#1`、`Shot 3` 等写法，但**同一次检查内镜号要能连续**（它据此判有没有缺镜） |
| 时长 | 必须能读成秒（`3 秒`、`3.5s`、`0:03`） |
| 画面 | 观众看到什么：主体、景别、构图、空间 |
| 做法 | 这一镜怎么做出来：技术/工具、输入素材、产出方式。**空着会被判红**——它正是"可执行"与"看起来漂亮"的分界 |
| 目的 | 这一镜承担什么表达目的。写不出目的的镜头，要么合并要么删 |
| 动源 | 这一镜的"动"从哪来：主体位移／运镜／切点／转场／元素动效／整段特效／静止。这是 `plan-check` 认的七个词，**它只是让下游对得上，不是创作限制**；判断方法在 `video-craft` §4 |
| 声音 | 这一镜的人声／音乐／音效／静默要做什么。**无声也是选择，但要明写**——全篇没有任何声音字段会被提示 |
| 素材 | 已有素材（指向项目内已授权副本）、待制作工件（写清用什么做）、真缺条件（写清影响与替代）。**标了"已具备"却没写具体文件会被判红** |

示例（逻辑是"先让观众看到系统从休眠进入运转"）：

> 画面：暗色机架中一列指示灯从左到右依次点亮，机位不动。
> 时长 3 秒。做法：授权机架照片作底图，代码遮罩逐盏叠加灯光。
> 声音：开头 2 秒只有低频电流声，最后 1 秒进旁白。动源：元素动效。
> 目的：让"这台机器在干活"这件事从静止变成事件。

**不要把七类动源写成风格要求**：某支片某一镜用了什么，不代表下一支也要用。比例与选择由片型、信息与用户审美决定。

### 1.2 意图摘要（人读）

完整作品的意图摘要与制作方案放在同一份 `plan.md`。`video-intent` 归纳，`video-plan` 承接。

它要能让没参与对话的人知道这几件事（用段落、清单或表格都行，不必逐项填）：

- **用户的原话**：关键处逐字引用，不改写。
- **你的理解**：每句都能指回某句原话——对不上就说明理解是编的。
- **不能丢的约束**与**明确不要的东西**：只放用户真说过的，不把你的推断混进去。
- **已有材料**：各是什么、能用到什么程度。
- **交给 AI 决定的**：用户明确授权你判断的部分。
- **仍然未知且会影响效果的**：缺口清单，不是问题清单。

**原话与理解必须分开写。** 用自己的总结替换用户原话，是最常见的走形。

### 1.3 修改单（人读，`video-review` 产出）

位置：作品文件夹 `feedback.md`，一次展示追加一组。

| # | 字段 | 写什么 |
|---|---|---|
| 1 | 改哪 | 修订号＋镜头号＋时间点，如 `r3 / 第 5 镜 / 12.4 秒` |
| 2 | 用户看到的 | 用户实际看到的、说出口的那句话；现象要具体，能带证据 id 就带 |
| 3 | 期望变成什么 | 用户想要的样子；你补的部分标"（我补的）" |
| 4 | 属于谁的问题 | 创作设计／执行／素材／工具／还没确定 |
| 5 | 波及范围 | 预计还要动哪些镜；哪些必须保持不变 |
| 6 | 改完怎么验 | 看哪几秒、听哪一段、量什么，什么算过 |

一条修改单对应**一次"看到的东西＋一句意见"**：用户连说三句就拆三条，合并会让后面的"保留/修补/重做"判断失去依据。第 2 项不许用"用户觉得不好"代替具体现象；没有证据就写"未取证"。

### 1.4 作品经验与资产（`tools/experience-library.js` 读写）

库根：`<工作区>/control-your-video/`，**默认不创建**。分类按**使用场景**七类：叙事与剧本／视觉与美术／角色与场景／镜头与运动／代码动画与特效／声音与配乐／剪辑与后期（也接受自定义场景名）。索引 `index.md`，一行一条，**由工具写，不要手写**。

状态只有三个：`待验证`／`在用`／`已废`。已废不参与检索。

条目字段与其现实限制（工具强制）：

| 字段 | 限制 | 说明 |
|---|---|---|
| 一句话 | ≤200 字 | 不是段落 |
| 可检验特征 | ≤400 字 | 怎么看出它在这一镜里确实发生了 |
| 适用条件 | ≤400 字 | 什么片型、什么条件下成立 |
| 反例或失效条件 | ≤400 字 | 什么时候不成立 |
| 出处 | ≤300 字 | 来自哪个作品/哪一版/哪个外部来源 |
| 验证程度 | 可空 | 跑过／只静态看过／作者自述 |
| 入库副本 | 可空 | 素材或工程的相对路径 |

**可检验特征与失效条件缺任一项，条目会被压回 `待验证`。** 这不是惩罚，是如实记录：说不清怎么验的东西，本来就是待验证。

写入必须带宿主批准对象（scope 决定是 `library-write` 还是 `library-asset-copy`），**读取也要批准**。

### 1.5 证据条目（`tools/evidence.js` 读写，键名固定）

位置：`work/evidence/index.json`。**英文键，脚本读**——这是本规范唯一允许并要求英文键名的地方，改名会让工具与审片对不上。

| 键 | 类型 | 写什么 |
|---|---|---|
| `id` | string | `r{修订}-s{镜号}-{时间}s-{用途}`，如 `r3-s05-12.4s-look`；派生图加后缀（`-crop`、`-sheet`） |
| `file` | string | 相对 `work/evidence/` 的文件名 |
| `revision` | string | 修订号，`r1`、`r2`…… |
| `shot` | number | 镜号 |
| `t` | number | 秒，保留一位小数 |
| `purpose` | string | 这条证据要回答什么类型的问题：`look`／`seam`／`text`／`motion`／`sync`／`mix`／`cover` |
| `source_sha256` | string | 被取证的源文件哈希 |
| `derived_from` | string \| null | 派生图的父条目 id；非派生为 `null` |
| `created` | string | ISO 时间，如 `2026-11-18T02:30:00+08:00` |
| `question` | string | 这条证据要回答的那一个问题，一句话 |
| `finding` | string | 看了之后的结论；没看就留 `""`，不许编 |
| `status` | string | `current`／`superseded` |

规则：

- **去重键 `(revision, shot, t, purpose)`**：同键只存一份，重复时复用旧 id。
- **默认只返回 `current`。** 重渲另起条目，旧条目标 `superseded`，**旧文件不删**（改完要能对照）。
- `question` 要能回答"是/不是"或"哪里不对"。写不出问题，说明这次不该取证。
- `finding` 为空时这条证据不算"看过"，结论里必须分开写"已看／未看／需用户决定"。
- `gc` 只清 `superseded`，且必须确认。

联系表（`sheet`）同样落在这个索引里：它的 `t` 是起始时间，`id` 带 `-sheet` 后缀，`file` 是一张多帧拼图。**联系表用来导航（该看哪几秒），不能用来判定运镜与节奏。**

### 1.6 完整方案与三个认可节点

1. 意图澄清与创意探索由主 Agent 负责。用户确认方向后再集中调研。
2. 在**单一** `plan.md` 里写明目标与关键约束、结构与总时长、所有镜头、视听一致性、**每镜的做法与资源路径**、小样验证点、交付要求；选定的关键技术、具体模型（若采用）、用途、预计费用上限与拟外发范围也写在这份方案里。
3. 用户看到完整方案后批准，宿主把批准绑定到**用户看到的那个内容版本**。文档里的状态文字只供阅读，不构成批准。普通技术优化在执行记录里留痕；重要创意或硬条件变更要重新审阅。
4. 按实际技术做出有代表性的小样，用户**看过并认可**后才进入全片。反馈有歧义先澄清。每轮修改交完整新片，保留已认可版本。

## 2. 知识放在哪里

### 2.1 五个承载位置

| 位置 | 放什么 | 不该放什么 |
|---|---|---|
| **Persona** | 身份、创作主体性、三个认可点与局部任务例外、能力入口、授权边界、真实反馈的诚实要求 | 专业教程、模型清单、资产路径、价格表、审美阈值、流程表 |
| **Skill 正文** | 稳定的专业判断：什么时候有这个问题、为什么错、有哪些相反路径、怎么选、怎么验、什么时候停 | 所有方法的完整实现、易腐的型号/价格资料、固定审美答案、强制格式 |
| **随包 references** | 高频、稳定、可离线用的深化知识：判据、条件、阈值与失效方式、工程做法 | 大量外部案例全文、受限材料的原文、会过期的 API 与价格 |
| **外部资产库** | 真实工程、素材、成片、案例与反例、长教程 | 未授权资料；也不能被当成"Agent 指令" |
| **工具/程序** | 哈希、解码、测量、预算、文件校验、授权状态 | 艺术判断与创作决定 |

**这不是加载顺序。** Agent 可以直接做、直接读 Skill、直接查库、直接用工具，也可组合。Skill 与外部库都能被独立需要，不需要先经过某个父级入口。

### 2.2 一条知识值不值得写进 Skill

三个问题都要过：

1. **删掉它，模型的行为会变差吗？** 不会就是空话（"要专业""注意节奏"）。
2. **它提供判断机制，还是只给一个答案？** 好知识说明条件与因果，能被迁移到没见过的输入。
3. **它稳定到值得随包吗？** 型号名、价格、平台上限、法条版本都会过期——这类写"去哪查、怎么核"，不写结论。

**示例只用来说明因果**：能揭示"几乎同样的一句话，在不同条件下为什么做出不同选择"的例子有价值；固定的"用户这样说，你就这样答"的行为示范不需要写。

### 2.3 当前入口与知识边界

| 入口 | 主责 | 明确不负责 |
|---|---|---|
| `video-craft` | 观众看到的与听到的这一层：症状分诊、叙事、视觉、运动、声音、剪辑、屏上字、跨域裁决、审美判断写法 | 选技术路线、方案结构与预算、成片取证 |
| `video-types` | 怎么做出来与每条路线独有的风险：代码/实拍/三维/生成/混合 | 视听判断与审美、镜头设计、发布合规 |
| `video-intent` | 感受词、参考片、材料 → 可用的创作意图；问不问的判断 | 片型结构、技术路线、成片复核 |
| `video-plan` | 单一 `plan.md`：结构、时长、逐镜可执行、小样选择、修改影响面 | 视听专业判断、技术路线取舍、取证 |
| `video-review` | 取证协议、修改单、**有依据的专业判断** | 替用户决定满不满意、直接改片、发布合规 |
| `video-release` | 能不能发/交/用：标识、许可、肖像、响度门槛、交付清点 | 创作质量、混音做法、平台后台操作 |
| `video-library` | 跨作品经验与资产的查、用、存；三种资产的分界 | 把方法写成 Skill、审计用户的研究库 |
| `video-skill-authoring` | 什么值得沉淀、怎么写能被触发、怎么验 | 本包各份内容、插件开发与发布 |

**边界靠指针维持**：相邻处写一句"这件事归 X"，不展开写别人的方法。重复一次原理，就有两个版本要维护。

## 3. 写 Skill 时必须满足的机制要求

这些由 DSH 的发现机制决定，不是风格偏好。

### 3.1 目录与 frontmatter

- 目录名 = `name` = kebab-case，三者必须一致；位置是 `skills/<name>/SKILL.md`，**DSH 不递归发现嵌套目录**。
- 必填 `name`、`description`。`description` 是唯一触发面。
- 布尔字段只写 `true/false`、`yes/no`、`on/off`、`1/0`；写成驼峰会**整条技能被静默丢弃**。

### 3.2 description

它是目录里唯一露出的东西，所以它也是唯一能决定"会不会被用上"的地方。

要写清三件事：**做什么**（具体能力，不是形容词）、**何时用**（用户会怎么说、什么场景撞上）、**不适用**（排除什么，并点名替代入口）。

- 关键触发词与负向边界都往前放：目录有长度上限，超长会截断，被截掉的部分等于没写。
- 写得能让模型在**自然语言请求**下认出它，而不是只有念出技能名才认得出。
- 不用"专业""高质量""一站式"这类自评词。
- 写完把几份描述排在一起读一遍：能不能一眼看出该用哪份。看不出就改这段，不改别人的。

### 3.3 references

- 位置只有一层：`skills/<name>/references/<file>.md`。文件名用小写字母、数字、连字符，不用中文名与空格。
- **不要再分子目录**：读取接口只认这一层，嵌套进去的参考模型永远读不到。
- **加载 Skill 时不会枚举 references**（机制如此）。所以正文里必须有一张索引：什么症状/任务 → 读哪份 → 读它是为了什么。没有这张表，参考文件等于不存在。
- 头两行写清"何时读、读它是为了什么"，且要写成**能被触发条件**（"用户说'像 PPT'且已确认不是剪辑节奏问题时"），不写"需要深入了解时"。
- 一主题一份；没有真内容就不建文件——只有标题的参考比没有更糟，它让索引看起来齐了。

### 3.4 长度

**没有行数上限的硬规定**，但有两个真实约束：

- Skill 正文是被加载进上下文的，越长越贵。判断要不要搬进 references 的判据是"它是不是每次加载都需要"，不是"它超过多少行"。
- 工具结果在压缩时有长度阈值，超长会被掐头去尾。正文控制在能被一次完整读到的量级内。

## 4. 数值、经验与示例

### 4.1 写进知识的每个数，都要回答三问

1. 它来自哪支片、哪种片型、什么分辨率/帧率/平台？
2. 换一种条件还成立吗？
3. 不成立时，替代判断是什么？

三问答不全，就把它降级为"某作者在某片型下的起点"，并在正文只留判断（"画面自己在动时镜头就不该再动"），不留数字；或者把它标成某类**交付参数**（平台响度、字幕行数），并注明随平台变。

**同一个数只留一处权威。** 出现两个数时，用**用途**分家而不是取平均：阅读型正文的行高、代码渲染的撞行线、平台交付的响度目标、作者经验的动作时长，是四件不同的事，各自成立。

### 4.2 这些口径已被否掉，不要再写回去

- 每镜必须有具体物体动作；标题／淡入／静态一律不合格
- 全片固定一种画风；固定三档尺寸；每章最多一个高光
- 固定三段小样；镜头规格固定若干行；每次必出四栏表／误差表
- 用户文稿可以删，但换个说法必须问；章节可互换就没有价值
- 编辑和延长都锁时长；所有生成严格靠关键帧对齐
- 能测量的一律测量、每次至少一个自动指标
- 没有音频通道就永远不能判定听感；MP4 不被读图工具接受就永远不能看画面
- 字符数是 Skill 合法性的硬门槛；description 必须完全互斥、核心与专项零重叠
- 受限内容换措辞就能以 MIT 随包分发
- "不能替用户判断好不好看"＝"Agent 不许作审美评价"

### 4.3 示例

- 有因果对照价值的例子写进正文：几乎同一句任务，在不同条件下为什么做出不同选择，成立条件是什么、误用会怎样。
- 真实案例、长教程、实际工程进外部资产库，按需读，不随包。
- 评测用的任务与标准答案不进 Skill，否则测的是背答案。
- **不设示例数量要求。** 一个说清因果的例子胜过三个格式一致的例子；一个例子都说不清时，先想清判断，不是先凑例子。

## 5. 来源与验证怎么写

正文末尾（或参考文件末尾）用两三行说明这份知识的来路：

```markdown
## 来源与限制
依据：<方法出处；能公开的写来源名与许可级别，需要回查的见仓库根 PROVENANCE.md>
未实测：<哪些没跑过、没生成过、没听过/看过>
缺口：<写的时候就知道还缺什么>
```

要求：

- **不写本机私有绝对路径。** 本包要能给别人用，路径只在仓库根的 `PROVENANCE.md` 里（开发记录，不随包分发）。
- **"未实测"要具体**：不是"效果待验证"，而是"这条只在一次修改里用过，没有第二支片复现"。
- 许可敏感的材料标级别（A/B/C/D）与用法（"只作研究线索，不随包"）。
- 不写"本 Skill 经过充分验证"。没验证就不写验证。
