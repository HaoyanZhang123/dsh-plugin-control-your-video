# control-your-video 编写规范

状态：Phase 0 接口约定，2026-11-18。本文件供 `packages/control-your-video/skills/` 下 13 份 Skill 的正文与参考使用。V1.3 已确认工作流优先。

**一句话**：接口只有一个定义处，正文只写判断，细节进参考，每份参考都必须写清"什么条件下读"。

## 0. 适用范围与优先级

1. 已确认的用户决策优先。写作参考按当前规则和具体场景判断。资产原件与本规范冲突时，按 §8 的条件化要求处理，不把作者配方写成通则。
2. 本规范只定"怎么写"和"共用什么"，不定每份 Skill 的专业内容。
3. 所有接口都是**人读的 Markdown 表或清单**，不造 JSON schema、不造 YAML 契约（§1.5 的证据索引除外，它要给脚本读）。能被 AI 直接读写，也能被用户看懂。
4. 改接口必须回到主对话改本文件。任何一份 Skill 不得自行增删字段、改名、另立一套。

## 1. 五个共享接口

通用规则：

- 每个接口只有一个定义处，就是本文件。Skill 正文**只用、不复述字段表**；需要说明时最多举 3 行示例，并写"字段定义见 `docs/编写规范.md` §1.x"。
- 字段名是中文词，用创作者能懂的说法，不用 `shot_id`、`beat`、`hook_type` 这类内部术语。
- 标"可空"的字段留空是正常状态，不是没写完；不要为了"填满"编内容。
- 接口是**当前作品的工作文件**，不是展示材料。不要求用户逐项确认，不要求每次输出全套。

### 1.1 镜头规格（方案的一部分）

全部镜头都要详细到可执行。镜头表和逐镜小节都能表达。每镜写出可定位的镜号和时长，观众看到或听到什么，有意停留或运动的具体做法，叙事作用、素材及制作路线、关键限制和需要保留的效果。没有对白或屏上字时可以明确说明。

例如，画面为暗色机架中一组灯从左到右依次点亮，机位不动，时长 3 秒。用授权机架照片作为底图，代码遮罩逐盏叠加灯光。开头 2 秒只有低频电流声，最后 1 秒进入旁白。逻辑是先让观众看到系统从休眠进入运转。机房布局与灯的位置保持稳定。

主体位移、运镜、剪切、转场、元素动效、整段特效和静止都是诊断画面的方法。具体比例由片型、信息和用户审美决定。遇到动效问题，可用相关 Skill 比对原意和画面证据。实际素材、声音和渲染时长回来后，复查全片节奏、尾部覆盖和同步。超出已确认的重要约束时重新对齐。

### 1.2 意图摘要（video-intent 产出）

**谁用**：video-plan（唯一消费方）。
**定义处**：只有 video-intent。
**位置**：作品文件夹 `brief.md` 顶部。

8 个字段，写成一张两列小表（字段 / 内容），不写成长文档：

| # | 字段 | 写什么 |
|---|---|---|
| 1 | 想要的感受 | **用户原话，逐字引用并加引号**，可以并列多句 |
| 2 | 我的理解 | AI 把原话翻成可感知的方向；与第 1 项**分开写**，不合并 |
| 3 | 给谁看、在哪看 | 观众与场合；不知道就写"未知" |
| 4 | 必须有的 | 内容、事实、元素、必须出现的镜头或说法 |
| 5 | 一定不能有的 | 用户明确排除的；没有就写"未提出" |
| 6 | 已有材料 | 用户给了什么：文稿、素材、参考片、截图，各能用到什么程度 |
| 7 | 交给 AI 决定的 | 用户明确授权给 AI 判断的部分 |
| 8 | 还没定的 | 真正会影响方向、但现在还没有答案的（最多 3 条） |

硬规则：

- 第 1 项**必须逐字**。改写用户原话、用自己的总结替换，是最常见的走形。
- 第 2 项必须能和第 1 项对得上：读的人要能看出"这句理解是从哪句话来的"。对不上就说明理解是编的。
- 不把 AI 的推断写进"必须有的""一定不能有的"。这两栏只放用户真说过的东西。
- 第 8 项不是问题清单，是缺口清单。写进去的东西不要求用户当场回答，由 video-plan 决定要不要问。

示例：

```markdown
| 字段 | 内容 |
|---|---|
| 想要的感受 | "想让人觉得这东西不是玩具，是真能干活的。""别太燃，燃了我反而不信。" |
| 我的理解 | 可信 > 激动。用真实细节（日志、机柜、手）换掉形容词；不加快切、不用大字金句。 |
| 给谁看、在哪看 | 给同行看的内部发布，横屏，2 分钟以内 |
| 必须有的 | DeepSeek 那行日志要真实可核；要有一次"灯亮起来"的时刻 |
| 一定不能有的 | 未提出 |
| 已有材料 | 一份 800 字产品说明（可改写成口播）；机房的现场照片 12 张（可用但不要露出机柜编号） |
| 交给 AI 决定的 | 结构、镜头、音乐 |
| 还没定的 | 要不要出现人；结尾落在机器还是人 |
```

### 1.3 修改单（video-review 产出）

**谁用**：video-plan（唯一消费方）。
**定义处**：只有 video-review。
**位置**：作品文件夹 `feedback.md`，一次展示追加一组。

6 个字段：

| # | 字段 | 写什么 |
|---|---|---|
| 1 | 改哪 | 修订号＋镜头号＋时间点，如 `r3 / 第 5 镜 / 12.4 秒` |
| 2 | 用户看到的 | 用户实际看到的、说出口的那句话；现象写具体 |
| 3 | 期望变成什么 | 用户想要的样子；用户没说的部分由 AI 补，补的要标"（我补的）" |
| 4 | 属于谁的问题 | 创作设计／执行／素材／工具／还没确定 |
| 5 | 波及范围 | 预计还要动哪些镜；哪些必须保持不变 |
| 6 | 改完怎么验 | 看哪几秒、听哪一段、看哪一帧，什么算过 |

硬规则：

- **一条修改单只对应一次"看到的东西＋一句意见"。用户连说三句就拆三条。** 合并成一条会让后面的"保留/修补/重做"判断失去依据。
- 第 2 项必须带证据（§1.5 的 id）或明确写"未取证"。不许用"用户觉得不好"代替具体现象。
- 第 4 项是判断，不是分类表演。判不了就写"还没确定"并说明缺什么才能判。
- 修改单不写"已修复"。修复状态由下一次展示时重写这张单来体现。

示例：

```markdown
| 字段 | 内容 |
|---|---|
| 改哪 | r3 / 第 5 镜 / 12.4 秒 |
| 用户看到的 | "这里字幕压在人脸上了"（证据 `r3-s05-12.4s-look`，抽帧 r3-s05-12.4s-look.png） |
| 期望变成什么 | 字不遮脸；字可以挪到画面下方三分之一（我补的：下方要留出进度条位置） |
| 属于谁的问题 | 执行（字幕安全区没算）——不是创作设计 |
| 波及范围 | 只改这一条字幕的位置；第 4—6 镜的字幕位置要一起核，其余不动 |
| 改完怎么验 | 看 11.0—14.0 秒连续三帧，字与脸不重叠；再扫全片有没有同样的压脸 |
```

### 1.4 可选的作品经验和资产

历史经验仅经当前用户授权后阅读。作品交付后才考虑收录。以具体使用场景归类，通过本地索引找相关内容。依用户选择复制项目素材，项目仍保留独立原件。

一条经验应包含具体做法、如何观察它的效果、适用条件与限制、来源以及验证程度。一次作品所见可以记录，并说明范围。出现重复时向用户展示冲突，由用户选择保留、合并或替换。

### 1.5 证据索引条目（video-review 与 evidence 工具共用）

**谁写**：`tools/evidence.js` 的 `extract` / `measure` 写入，video-review 补 `question` / `finding`。
**谁读**：video-review（`recall`）、video-plan（通过修改单间接读）。
**位置**：作品文件夹 `work/evidence/index.json`，一条一行（JSON Lines 或数组都可，工具按数组读写）。

字段（**英文键，脚本读**，这是本规范唯一允许的英文键名）：

| 键 | 类型 | 写什么 |
|---|---|---|
| `id` | string | `r{修订}-s{镜号}-{时间}s-{用途}`，如 `r3-s05-12.4s-look`；派生图加后缀 `-crop` |
| `file` | string | 相对 `work/evidence/` 的文件名 |
| `revision` | string | 修订号，`r1`、`r2`…… |
| `shot` | number | 镜号 |
| `t` | number | 秒，保留一位小数 |
| `purpose` | string | 这条证据要回答什么类型的问题：`look`／`seam`／`text`／`motion`／`sync`／`mix`／`cover` |
| `source_sha256` | string | 被取证的源文件（成片或素材）的哈希 |
| `derived_from` | string \| null | 派生图的父条目 id；非派生为 `null` |
| `created` | string | ISO 时间，`2026-11-18T02:30:00+08:00` |
| `question` | string | 这条证据要回答的那一个问题，一句话 |
| `finding` | string | 看了之后的结论；没看就留 `""`，不许编 |
| `status` | string | `current`／`superseded` |

硬规则：

- **去重键 `(revision, shot, t, purpose)`**：同一键只存一份。重复时复用旧 id，不新建。
- **默认只返回 `current`。** 重渲不覆盖旧证据：新修订另起条目，旧条目标 `superseded`，旧文件不删。
- `question` 必须是一个能回答"是/不是"或"哪里不对"的问题。写不出问题，说明这次不该取证。
- `finding` 为空时，这条证据不算"看过"。review 的结论里必须区分"已看""未看""需人判断"。
- `gc` 只清 `superseded`，且必须确认。不删 `current`。

示例：

```json
[
  {
    "id": "r3-s05-12.4s-look",
    "file": "r3-s05-12.4s-look.png",
    "revision": "r3",
    "shot": 5,
    "t": 12.4,
    "purpose": "look",
    "source_sha256": "…",
    "derived_from": null,
    "created": "2026-11-18T02:30:00+08:00",
    "question": "12.4 秒这条字幕有没有压到人脸？",
    "finding": "压到下颌线，字底边与下巴重叠约 12px。",
    "status": "current"
  }
]
```

### 1.6 完整方案与三个认可节点

1. 文字澄清与创意探索由主 Agent 负责。用户确认方向后再集中调研。
2. 在单一的计划文件中写明目标和关键约束、结构和总时长、所有镜头、视听一致性、制作和资源路径、小样验证点和交付要求。已有资源须能定位并核实。计划内待制作工件要写清执行条件与方法。缺关键条件时先处理。
3. 检查并审阅完整方案。由宿主把用户批准绑定至用户看到的内容版本，文档中的状态文字只供阅读。普通技术优化可在批准范围内记录和执行。重要创意或硬性条件变更需重新审阅。
4. 按实际技术完成有代表性的小样，用户看过并认可后开始全片。有歧义的审片反馈先澄清。每轮修改提供完整新成片，保留已认可内容。

## 2. 13 份的分工与边界

每份只做自己那一列。相邻处**写一句指针**（"这件事归 X，见那个 Skill"），不展开写别人的方法。

| # | Skill | 主责 | 明确不负责 | 主要邻居 | 族内参考（主题，可按资产调整，不越界） |
|---|---|---|---|---|---|
| 1 | `video-intent` | 把说不清的感受、零散材料、参考片变成 §1.2 的意图摘要；判断哪些该问、哪些该自己补 | 定片型与结构；写方案；写台词 | → video-plan | 感觉词到视听的映射；问题预算；意图摘要的正例与反例 |
| 2 | `video-plan` | 片型、结构、时长预算、§1.1 镜头规格、参考重构、小样选择、修改范围判断、制作路径与交付组织 | 提示词写法；声音做法；剪辑执行；视觉系统细则；审片取证 | 全部 | 片型；结构；时长；分镜与镜头规格；参考重构；小样 |
| 3 | `video-script` | 口播、解说、标题的字；文章到口播；AI 味清理；口播稿的事实边界 | 声音路线（sound）；镜头安排（plan）；字幕排版（edit） | plan、sound、edit | 旁白原则；文章到口播；标题与开场 |
| 4 | `video-visual` | 设计系统（色/字/间距/层级）、版式通则、封面、3D 与空间 | 动效（motion）；代码实现（code-visual）；剪辑 | plan、motion、code-visual | 设计系统；版式通则；封面；3D 与空间 |
| 5 | `video-motion` | 动效为什么像 PPT、缓动与运动路线、效果库检索 | **转场与整体节奏（归 video-edit）**；剪辑点；字幕 | visual、edit | 动画原则与缓动；效果库；转场只留指针 |
| 6 | `video-prompting` | 把 §1.1 翻成所选模型/工具能接受的输入；参考用途；失败归因 | 镜头设计、叙事；声音；视觉系统；模型选型采购 | plan、visual | 一模型一份（Veo／Sora 2／Seedance／MiniMax／Luma／通用）；失败归因 |
| 7 | `video-code-visual` | 用代码出画面（Canvas/three/HTML 到帧）、出帧管线、代码画面的验收 | 设计系统；动效原则；提示词 | visual、motion | 出帧管线；Canvas 与 three；代码画面验收 |
| 8 | `video-edit` | **转场与节奏（唯一归属）**、剪辑点、字幕规范、时长重算与重定时 | 时长预算的初次分配（归 plan）；镜头设计；声音设计 | plan、sound、motion | 转场；字幕规范；重算与重定时 |
| 9 | `video-sound` | **人声路线（唯一归属）**、表演与发音、音乐音效与静默、同步与混音、局部重配 | 时长预算（归 plan，只写声音侧影响）；字幕文本；镜头 | script、edit、plan | 人声路线；音乐与音效；同步与混音 |
| 10 | `video-review` | 带着问题取真实证据、观察清单、缺陷库、修复策略、§1.3 修改单、§1.5 证据条目 | 替用户判断好不好看；直接改片（回到 plan） | plan、edit、sound | 观察清单；缺陷库；修复策略 |
| 11 | `video-release` | 能不能发：验收口径、AI 标识、许可与肖像、响度、交付清单 | 创作质量；渲染技术；平台账号操作 | review、sound | 验收口径；AI 标识；权利与肖像；响度与交付 |
| 12 | `video-library` | §1.4 库结构、条目格式、写入与整理规则、什么时候读库 | 替用户定审美偏好；把方法写成 Skill | skill-authoring、全部 | 库规范；条目格式；整理规则 |
| 13 | `video-skill-authoring` | 把一套做法提炼成技能、本包约定、验证办法 | 本包 13 份自身的内容 | library | 方法提炼；本包约定；验证 |

拆不拆看三问（来自产品框架）：用户会不会直接这么说；脱离完整流程还能不能独立用；正文能不能 150 行说清。三条都不成立就并回去，不硬拆。

## 3. SKILL.md 模板

每份正文固定这个骨架，**总行数 ≤ 150**（含 frontmatter 与空行）。建议 90—130 行。超过 6000 字符就要开始往 references 搬。

```markdown
---
name: video-xxx
description: "<三段：做什么。何时用。不适用。>"
---

# 标题（与 name 对应的中文名）

## 1. 先判断这次是什么任务
## 2. 决定顺序：第一步做什么、什么条件下换路
## 3. 产出格式（只给字段名和示例，定义指向 docs/编写规范.md）
## 4. 边界：不做什么，遇到什么转给谁
## 按需参考
## 来源与限制
```

正文只放四类东西：

1. **判断顺序**：先看什么、看到什么走哪条路。
2. **决策规则**：什么条件下选 A 不选 B，代价是什么。
3. **产出格式**：这次要给用户/下游什么，字段名＋一行示例。
4. **边界与指针**：不做什么；什么情况转给哪个 Skill。

**不放进正文**：命令、参数、模型清单、资产原文摘录、完整案例长文、表格模板全文。这些进 references。

## 4. description 三段写法

`description` 是唯一触发面，三条硬线：

| 段 | 写什么 | 位置 | 字数 |
|---|---|---|---|
| 一、做什么 | 这个 Skill 实际能替用户完成的事，用动作句 | 最前 | ≤ 90 字 |
| 二、何时用 | 用户会怎么说、什么场景会撞上 | 中间 | ≤ 120 字 |
| 三、不适用 | 明确排除什么，并点名该用哪个 Skill | 最后，但必须在前 220 字符内出现首个"不"边界 | ≤ 90 字 |

- **总长 ≤ 320 字符**（中文字按 1 计）。目录上限是 500，超长会被截断；把负向边界放在 500 之后等于没写。
- 三段之间用句号分隔，不加小标题、不加换行、不加 `[]`。
- "不适用"必须点名**具体的替代 Skill 名**，不能写"用别的技能"。
- 不用"专业""高质量""一站式""强大"这类词；描述里出现形容词夸奖自己，等于没写触发面。
- 写完自检：把 13 条排在一起读，能不能一眼看出该用哪条。看不出就改这一段，不改别人的。

模板：

```
把<什么事>做成<什么结果>，并在<什么情况下>给出<什么判断>。当用户说<原话示例1>、<原话示例2>，或<场景>时使用。不负责<甲>（用 <skill-a>）、不负责<乙>（用 <skill-b>）。
```

## 5. references 规范

### 5.1 文件与命名

- 目录：`skills/<name>/references/`
- 文件名：小写 ASCII、连字符分隔、`.md`，如 `narration-principles.md`、`model-veo.md`。不用中文文件名、不用空格、不用编号前缀。
- 一主题一份。一份超过 250 行就考虑拆；少于 40 行且只服务一个判断，考虑并回正文。
- 不建空目录、不建占位文件。没有真内容就不建。

### 5.2 头两行固定

```markdown
# <中文标题>

> 何时读：<具体条件，一句话>。读它是为了<解决什么判断>。
```

"何时读"必须写成**能被触发条件**，不能写"需要时读""想了解更多时读"。

反面例子（等于没写）：`> 何时读：需要深入了解动效时。`
正面例子：`> 何时读：用户说"像 PPT""太死板"，且已经确认不是剪辑节奏问题时。`

### 5.3 SKILL.md 里的"按需参考"

每份正文必须有"按需参考"一节，逐条列出：

```markdown
- 用户说"像 PPT""太死板" → `references/motion-principles.md`
- 要写某个模型的提示词，且已选定模型 → `references/model-<型号>.md`
- 素材和参考片对不上，要先判断差在哪 → `references/reference-rebuild.md`
```

格式固定：**触发条件 → 文件名**。只写文件名、不写触发条件，模型不会去读。

## 6. 每份必带的四件东西

| 件 | 要求 | 位置 |
|---|---|---|
| 3 个具体判断示例 | 格式：`用户这么说：… → 你这样判断：… → 所以你这样做：…`。必须是真能发生的对话，不许写"当用户需要 X 时" | 正文中段，或专列一节 |
| 1 条反例 | 看起来合理、实际会错的做法；写清**错在哪一步**，不只说"这样不好" | 示例之后，标"反例" |
| 1 处"不适用" | 这件方法在什么片型/条件下不成立，或这个 Skill 不该被用来做什么 | 正文"边界"一节 |
| 来源与限制 | 见 §9 | 正文最后一节 |

示例不许抽象。判断示例里必须出现**具体的用户原话**和**具体的处置**（改哪一镜、用哪条路、说什么话）。

## 7. 禁止清单

出现以下任一，视为不合格：

| # | 禁止 | 判断方法 |
|---|---|---|
| 1 | 空话 | 删掉这句，结果会变差吗？不会就是空话。"要专业""注意质量""保持统一""多练习"一律删 |
| 2 | 通用常识 | 任何领域的人都写得出的句子（"好片子要有好故事"）。专业增量必须是"只有做过的人才知道的判断" |
| 3 | 逐阶段审批 | "每一步都要用户拍板""每做完一镜问一次""逐项确认"。**但意图确认、方案定稿、小样验收是三个必经确认点**，见 §1.6；其余环节自主推进 |
| 4 | 内部管理表格 | 阶段表、置信度、四栏对照表、误差表作为**必出物**。判断可以内部做，不必全部输出 |
| 5 | 把方法写进 persona | persona 只放身份与原则。任何具体做法、清单、参数都不进 persona |
| 6 | 整段搬运资产原文 | 只提炼方法。受限许可材料（C/D 级）只作研究线索，不作随包文本 |
| 7 | 假定模型/工具能力 | "某模型一定能锁时长""这个工具一定支持局部重配"。写成"先查当前能力，查不到就降级" |
| 8 | 假装看过 | "已检查画面""听过混音"。没输入就说没输入，并写清缺什么 |
| 9 | 一套规则套所有片 | 把某个作者路线的数值（2—6 秒、≤8 字、禁蓝紫、≥170px 主角）写成通用门禁 |
| 10 | 用形容词替代判断 | "更有张力""更高级"。要么给可感知的视听选择，要么不给 |

写完自查一遍：逐段问"删掉这段，模型的行为会变差吗"。答案是否，删。

## 8. 唯一归属与条件化

### 8.1 三处必须裁决的重复

| 重叠点 | 唯一归属 | 另一方的写法 |
|---|---|---|
| 转场与节奏 | `video-edit` | `video-motion` 只留一句指针："转场与整体节奏归 video-edit，这里只管单个元素怎么动" |
| 时长预算 | `video-plan` | `video-sound` 只写声音侧影响（"这句配音会让这一镜多 0.8 秒，要不要回来调 plan"），不重算全片预算 |
| 镜头规格 | `video-plan` | 其他 Skill 一律写"字段定义见 `docs/编写规范.md` §1.1"，最多举 1 行示例，不列字段表 |

另加一条本次裁决：**人声路线**（真人录音／TTS／已有配音／无人声）唯一归属 `video-sound`。`video-script` 只写"这句话念出来顺不顺"，不选路线。

### 8.2 资产数值的条件化

读到的任何具体数值、禁令、阈值，写进正文前必须回答三问：

1. 它来自哪支片、哪种片型？
2. 换一种片型还成立吗？
3. 不成立时，替代判断是什么？

三问答不全，就把它降级为 references 里的"某作者在某片型下的做法"，并在正文只留**判断**（"画面自己在动时镜头就不该再动"），不留数字。

已被明确否掉、不得写回去的口径（来自能力骨架 §5）：

- 每镜必须有具体物体动作；标题／淡入／静态一律不合格
- 全片固定一种画风；固定三档尺寸；每章最多一个高光
- 固定三段小样；镜头规格固定若干行；每次必出四栏表／误差表
- 用户文稿可以删，但换说法必问；章节可互换就没有价值
- 编辑和延长都锁时长；所有生成严格靠关键帧对齐
- 能测量的一律测量、每次至少一个自动指标
- 无音频通道／MP4 不被读图工具接受，因此永远不能听／看视频
- 8000 字符是 Skill 合法性硬门槛
- description 必须完全互斥、核心与专项零重叠
- 受限内容换措辞就能 MIT 随包

## 9. "来源与限制"怎么写

正文最后一节，固定三段，各 2—4 行：

```markdown
## 来源与限制

依据：<具体文件路径或资产目录，列 2—5 条>。这些是本轮实际读过的，不是转述。
未实测：<这份方法里哪些没有跑过、没有生成过、没有听过／看过>。
缺口：<写的时候就知道还缺什么；不确定的记进待确认清单，不编>。
```

要求：

- 路径必须真实存在。写之前核对过，不凭印象。
- **路径写成从工作区根开始的完整相对路径**，例如 `resources/research/已确认资产/03-美术图像与提示词/03-oil-ui-references/visual-language.md`。
  禁止三种写法：只写文件名（`visual-language.md`，同名文件会混）、省略类目（`03-oil-ui-references/...`）、用 `…/` 省略前段（读的人拼不出来）。
  这些资产**不随包分发**；写它们的用途是标明方法出处与可回查位置，不是承诺运行时一定读得到。
- "未实测"必须具体：不是"效果待验证"，而是"机房低频垫底这条只在 r2→r3 一次修改里用过，没有第二支片复现"。
- 许可敏感的材料要标级（A/B/C/D）与用法（"只作研究线索，不随包"）。
- 不写"本 Skill 经过充分验证"。没验证就不写验证。
