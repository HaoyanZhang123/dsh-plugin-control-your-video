# 库的结构与读写规则

> 何时读：要新建库、判断这次该读库还是写库、或某条东西该写回库还是写回作品文件夹时。读它是为了分清"跨作品的事实"与"这一支片的事实"，不让两种记录互相覆盖。

## 一、每个事实只有一个所有者

库和作品文件夹会写同一类内容（做法、理由、修改），所以先定谁拥有什么。判据是**这条事实换了作品还成立吗**：

| 事实 | 所有者 | 为什么不在库里 |
|---|---|---|
| 用户这一次想要的感受、必须有的、一定不能有的 | 作品 `plan.md` 中的创作意图（§1.2） | 这些要求只适用于当前作品 |
| 这一支片的镜头、时长、结构 | 作品 `plan.md`（§1.1） | 换一支片就变 |
| 某几秒到底哪里不对、改完怎么验 | 作品 `feedback.md` 与 `work/evidence/`（§1.3、§1.5） | 证据挂在修订上，不跨片 |
| 用户一贯不喜欢什么 | 库 `preferences.md` | 跨片，但只由用户自己说 |
| 某类片子里 X 会导致 Y，怎么看出来 | 库 `methods/` | 跨片、可检验 |
| 某模型或工具在这台机器上的实测结果 | 库 `prompts/` | 换模型或版本就废，必须带失效条件 |
| 某支参考片借什么、不搬什么 | 库 `references/` | 一支参考片常服务多支作品 |
| 一个可复用的段落结构 | 库 `templates/` | 结构可跨题材 |
| 踩过的坑与识别特征 | 库 `lessons.md` | 坑会重复 |

**改哪个所有者**，按变了的东西判，不按谁先提的判：

- 用户的目标、事实、约束变了 → 改作品 `plan.md` 中的创作意图
- 故事、镜头逻辑、视觉系统、表演变了 → 改作品 `plan.md`
- 只是提示词微调、候选换了、参数改了 → 改 `prompts/` 里的配方或本次生成输入，不进方法卡
- 参考片有了新证据 → 改库 `references/` 那条，再回头看要不要动作品
- 同一种失败第二次出现 → 先写 `lessons.md`，两支片都成立才提成 `methods/`

一条事实落在两个所有者手里，就等于没有所有者：下次两边不一致时，没人知道该信哪个。

## 二、建立

位置与结构见 `docs/编写规范.md` §1.4，本份不复述目录树。

**先分清两件事：读库和建库。** 库里没有 `index.md` 时，读库的结果是"没有可读的旧条目"，到此为止——**不要为了读而建库**。只有真要写第一条时才建，判据是"用户已经同意记这一条"（见第五节）。

建的时候按三步：

1. **先看 `index.md` 在不在**。在就只追加，不覆盖已有内容；不在就在这一步建它，目录随它建。
2. **只建这次真要写的那一个文件**。不预建空目录，不写占位文件，不为了"结构完整"先把七个位置铺开。第一支片通常只产出 `index.md` 加一到两个条目文件。
3. **建完把位置告诉用户一次**（`<工作区>/control-your-video/`），之后不再重复解释。

一句话给用户听的说法：**"你的库现在是空的，第一支片结束后才会有第一条。"** 这句话在整支片里只说一次，用户不追问就不展开讲七个目录。

**库跟着工作区走。** 换一个工作区就是另一个库，插件不跨工作区合并、不提供迁移工具。要在新工作区沿用旧库，那是把整个 `control-your-video/` 目录复制过去，属于用户自己的文件操作。

## 三、这条东西放哪个文件

按顺序问，第一个答"是"就停：

1. 主语是"我"（用户的口味、禁令）→ `preferences.md`
2. 说得出适用条件与失效条件，且换一支片仍成立 → `methods/`
3. 只是某个模型、工具或参数在这台机器上的实测结果 → `prompts/`
4. 是某支参考片的拆解 → `references/`
5. 是一个可复用的段落结构（几段、什么顺序、多长）→ `templates/`
6. 是一种失败现象加识别特征 → `lessons.md`
7. 都不是 → 不写

`methods/` 收"这样做会怎样"，`prompts/` 收"这个模型吃这套"。两处混装是最常见的错：把模型参数写进方法卡，下次换了模型，整条方法跟着一起作废。

## 四、什么时候读

四个触发（要点见正文）。读的时候守三条：

- **先 `index.md`，一行一条**。它是唯一入口；没进 `index.md` 的条目按不存在处理。
- **只打开命中的那几条**，最多两三条。全库通读会把旧结论连同意外作废的结论一起带进上下文。
- **连着失效条件一起读**。只读一句话就套用，是把别人的片型当成自己的片型——条目里那句"不适用"往往比方法本身更值钱。

命中条目与这次的适用条件不符时，把它降级成"某片型下的做法"，在对话里说清哪里不一样，不硬套。

## 五、什么时候写

三个触发（要点见正文）。写入前要能当场答出四问：

1. 下次在什么片型、什么预算、什么工具下它还成立
2. 怎么从画面、声音或做法上看出它在用
3. 什么情况下它不成立
4. 出处是哪支片、哪次修改、或哪份资产

四问答不全 → 不写，或先写进 `lessons.md` 当现象记录。写之前问用户一句要不要记，用户说不用就不记。

写完在 `index.md` 追加一行，格式见 §1.4。只追加、只改自己那行，不动别人写的行。

## 六、"用过"怎么算

三个月清理靠这一条判，所以要写死口径。算用过：

- 被读进某支片的方案、提示词或声音设计
- 被作品文件或其他条目显式引用
- 用户在对话里点名采用

不算用过：检索到但没采用；打开看了没用；生成时顺带读过。三个月从**最后一次算用过的那天**起算，不是从创建日。

## 七、写坏了怎么修

| 坏法 | 处置 |
|---|---|
| 字段缺一半 | 能补就补；补不出来就降级成 `preferences.md` 或 `lessons.md` 里的一句，不留半条方法卡 |
| 出处丢了 | 状态退到"待验证"，并在条目里写清缺哪一段（哪支片、哪次修改） |
| 一条里两件事 | 拆两条，各自找出处；不合并成一条"综合经验" |
| 与另一条矛盾 | 先按适用条件判是不是两种片型各自成立；不是就留更晚的、把另一条写成它的失效条件 |

修的时候不改 `index.md` 之外的东西，也不写变更记录——库不是日志。

## 八、不做的事

不建数据库、不做状态机、不建全连接依赖图（D-09）：没有索引服务，检索靠 `index.md` 与文件名。不加标签体系、不加评分、不加条目间互相引用（除出处那句）。

依据与验证范围见仓库根的 `PROVENANCE.md`（开发记录，不随包发布）。
