# 跨作品经验与资产

本份管一件事：**这台机器上、这个工作区里，用户选择保留的创作经验，怎么查、怎么用、怎么存。**

先说清三种不同的东西，不要混：

| 是什么 | 在哪 | 谁能读 | 谁维护 |
|---|---|---|---|
| 本次项目的素材与工程 | 项目目录 `assets/`、`work/` | 已授权即可 | `cyv` 的 `import_assets` 等 |
| 跨作品经验库 | `<工作区>/control-your-video/` | **每次检索都要用户允许** | 本份 + `cyv save_experience` |
| 用户自己的研究/出处库 | 用户机器上，位置由用户决定 | 只有本次明确授权才可查 | 不归本插件管理 |

**第三条不是你造的，也不该被当成第二条。** 研究库（案例、原文、工程、素材集）有自己的组织方式与许可标记；本插件不建索引、不复制、不改动它。用户让你参考其中的东西时，按他给的路径只读地看，并遵守他说的范围。

## 1. 查历史：先问允许，再查小范围

新项目出现相似问题时：

1. **先说明它能帮什么**，再问是否允许查。不要说"我先查一下你的库"。
2. 允许后用 `cyv` 的 `read_experience`，带上当前问题（不是宽泛关键词）。
3. **只查当前问题**，不把上个项目的风格自动当成这次偏好。用户认可过一种颜色或节奏，不等于以后都照用。
4. 查到的东西要判适用条件：它是什么片型、什么技术条件下成立的，验证到什么程度。带着条件和保留地说，不要当结论直接搬。

库不存在是正常状态。这时直接说"还没有库，不影响这次创作"，不要造一个。

## 2. 交付后沉淀：少而准

作品交付并且用户认可之后，可以建议收录**少量**真正有复用价值的内容。建议时要说清：

- 它来自哪个作品、哪一版；
- 实际效果如何（用户当时怎么评价的）；
- 在什么条件下成立、什么时候会失效；
- 验证到什么程度（跑过／只静态看过／作者自述）。

**一次成功不等于方法成立。** 只有结果说不出为什么的，写进库时要标"待验证"，不要包装成"已验证的做法"。

用户选择收录后用 `cyv save_experience`，把项目文件复制进库、项目原件保留。目录分类与条目状态**以工具返回为准**。

## 3. 库的真实结构（照它写，别照想象写）

- 库根：`<工作区>/control-your-video/`，**默认不创建**，第一次收录时才建。
- 分类按**使用场景**，七类：叙事与剧本 / 视觉与美术 / 角色与场景 / 镜头与运动 / 代码动画与特效 / 声音与配乐 / 剪辑与后期。也接受自定义场景名。
- 索引：库根 `index.md`，一行一条，由工具写。**不要手写索引**，也不要按"文件类型"另建目录——那样工具读不到。
- 状态只有三个：待验证 / 在用 / 已废。已废的条目不参与检索。
- 条目正文由工具按固定字段落盘（标题、一句话、可检验特征、适用条件、反例或失效条件、出处、验证程度、入库副本、日期与状态、推荐理由、入库授权记录）。长句会被压回，**字段是"一句话"不是"一段话"**。

**收录的不是摘要，是能再用一次的东西**：素材副本、工程、可运行的代码、真实成片。只留一段文字描述，下一个人用不上。

## 4. 重名、相似与替换

工具报冲突时不要自己决定覆盖。带着来源与差异让用户选：

| 情况 | 建议 |
|---|---|
| 同内容重复 | 保留一份，另一份不复制 |
| 同一问题、不同做法 | 两份并存，各自写清适用条件 |
| 新版本更好但旧的仍有人用 | 并存，旧条目标为"在用"但注明被哪个超越 |
| 旧条目确认失效 | 标"已废"，**不删除**（删除会丢掉"当初为什么这么做"） |

## 5. 偏好与约束要分开

- **长期偏好**：用户跨作品一致的选择（"我从来不用大字口号"）→ 进偏好类记录。
- **当次约束**：这次客户的品牌色、这次的平台限制 → 留在本项目，不进库。

把当次约束写成长期偏好，下一个项目就会被无理由地砍掉一半选择。

## 6. 什么时候不要收录

- 用户没有明确说要留；
- 只有结果、说不出为什么；
- 素材的权利不允许这样保存或复用；
- 内容是别人的作品而不是这套做法；
- 它只是一次性的技术细节（某次导出的临时参数），下次不会再用。

## 7. 边界

- **不把方法写成 Skill**：那是 `video-skill-authoring`。本份只记"这一次可用的东西"。
- **不审计、不搬迁用户的研究库**：那需要用户明确授权与独立的作业范围，不是本插件顺手做的事。
- **不承诺"库里有的就一定好用"**：验证程度写在条目里，读的人要看。
- **不因为库里有旧案例就改当前作品的目标**：用户这次的意图优先。
- **不手写索引、不按格式另建目录**：库的读写走工具，手改会让索引与文件不一致。

## 8. 判断示例

**"以前那个粒子散聚的效果是怎么做的，能用上吗？"** → 判断：这是查历史的请求，但要先确认授权，也要判适用条件。 → 做法：说明"库里可能有一条与运动相关的记录，可以查吗"，允许后按"粒子 聚合 效果"查场景"镜头与运动"；查到后先报条件（当时是哪种片型、什么实现、验证到哪一步），再说"这一镜的目标不同，可以借机制但需要改时长与配色"。

**"把这套记下来，以后都用。"** → 判断：要分堆——这次的做法里，哪部分是方法（有因果、有反例、能迁移），哪部分是这个客户的偏好。 → 做法：方法部分建议收录成库条目；偏好部分建议记成偏好；成套判断真要复用成 Skill 时转 `video-skill-authoring`。

**反例**：用户说"上次那种蓝紫色挺好，这次也用"，你直接把库里的配色搬进新片。错在把一次选择当成了偏好，也没有判这次的主体与光是否吃得下那个色。正确做法是给条件："上次那个蓝紫是在暖光实景上压得住，这次主体是白色产品，同色会把主体吃掉；要不要换成同色系但更浅的一档？"
