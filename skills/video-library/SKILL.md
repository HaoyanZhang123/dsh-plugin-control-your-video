# 资产库

## 1. 先判断这次该不该碰库

三个问题依次过；第一问答"不"就结束，不进库：

1. **这东西下次换一支片还成立吗？** 只在这一支片成立的选择、这一次的口味、这一版的参数，属于作品文件夹，不属于库。
2. **说得出"怎么看出它在用"吗？** 说不出就说明还没想清，先留在作品里，等它第二次被证明再说。
3. **用户认可了吗？** 默认不入库。一支片交付、用户说好，才考虑记一条。

"这次用红色吧"不是库的事。用户接着说"我以后都不想看到蓝紫"才是，而且进 `preferences.md`，不进 `methods/`。

## 2. 什么时候读，怎么读

四个触发，缺一个就不读：

- 要复用以前的做法（同一片型、同一类镜头、同一条工具路线）
- 用户问"以前那支片怎么弄的来着"
- 同一种失败第二次出现，要查是不是旧条目已经记过
- 要给建议，但不确定自己是不是在重复造轮子

**先看 `index.md` 在不在。** 不在就说明库还没建，这是新用户的正常状态，不是缺陷：直接告诉用户"你的库现在是空的，第一支片结束后才会有第一条"，然后照常做事，不要建空目录、不要铺占位文件、不要因为他没有库就去补一份通用资料。用户问"库在哪"或"我该怎么建"时，只说一句位置与一句话理由，不展开讲七个目录。

读法只有一种：**先读 `index.md`，一行一条**，按一句话、日期、状态筛出候选，只打开命中的那几条。整库通读会让上下文被旧结论占满，还会把过时条目当现行做法用。状态是 `已废` 的跳过。

## 3. 什么时候写，写几条

| 触发 | 处置 |
|---|---|
| 一支片做完，用户认可其中某个做法 | 记一条，写入前问用户要不要记 |
| 用户说"这个做法记下来" | 记，但先把它压成一句可检验的话 |
| 同一个坑第二次踩到 | 记；第一次没记，说明当时判断错了它的复用价值 |

只写 **一条**。塞三件事的条目三个月后没人打开：用的时候不知道信哪一半，改的时候不知道改的是哪一条。

**写之前问一句**，问的是这句话："这条要记成 `methods/<名字>.md`，一句话是……，要不要记？"用户说不用，就不记，也不在别处留草稿。不替用户决定"这值得记"。

条目字段与 `index.md` 的单行格式见 `docs/编写规范.md` §1.4，本份不重列。一行：

```markdown
- 2026-11-18 · 机房开场先给低频电流声、人声进来再推音乐 · methods/low-freq-open.md · 待验证
```

写坏了不必推倒重来，分三种处置：字段缺一半 → 补，补不出来就降级成 `preferences.md` 或 `lessons.md` 里的一句；出处找不到 → 状态退到"待验证"，并在条目里写清缺的是哪一段（哪支片、哪次修改）；一条里其实有两件事 → 拆成两条，各自找出处。

## 4. 什么叫可检验

一条记录能不能进库，只看三关：

- **看得见**：能指向画面、声音或做法上的具体差别，不是"更舒服""更有质感"
- **说得出不成立**：写得出一个它会失效的场合；写不出反例，说明还没想清
- **下次还成立**：适用条件窄到能判断"这次算不算在里面"

最省事的一次自检：把这条念给没参与讨论的人，他能不能知道**什么时候用**、**用的时候看什么**。两样缺一样，就不该进 `index.md`。

## 5. 偏好与方法的分界

- 偏好进 `preferences.md`，主语是"我"：`我不喜欢蓝紫。`
- 方法进 `methods/`，主语是片子：`这类片子里蓝紫会抢主体，因为背景本来就暗。`

分辨话术：**把这句话的主语换成"这类片子里"，读一遍。** 读得通是方法，读不通是偏好。偏好也只由用户自己说；不问就不写，不把"他上次用了红色"推断成"他喜欢红色"。

## 6. 判断示例

用户这么说："这个做法记下来。" → 你这样判断：先问是哪一个做法。他刚看的是第 3 镜接缝处的处理，还是整支片的开场结构；前者是一条可检验的做法，后者现在还只是印象。 → 所以你这样做：把第 3 镜的做法压成一句"接缝前留 4 帧空场再切"，问一句"这样记？"，用户同意才写进 `methods/`；"开场结构好"不写，等第二支片也能复现再说。

用户这么说："以前那支片怎么弄的来着。" → 你这样判断：这是读库触发，但先确认他问的是画面做法、提示词配方还是声音；三者在库里不在同一个位置。 → 所以你这样做：读 `index.md` 一行一条，按那支片的片型与他提到的现象筛出两三行，只打开这几条；答的时候给条目名加一句话，不把整条念一遍，也不把 `已废` 的当现行做法。

用户这么说："把库里没用的删了吧。" → 你这样判断：不能按"看起来没用"删，要按"有没有被用过"删。 → 所以你这样做：逐条问三个月内它有没有被读进某支片的方案、提示词或声音设计，有没有被别的文件引用；都没有才是删除候选。删之前再确认它不是某支片唯一的记录（出处那次修改，作品文件夹里还在不在），删完同步删 `index.md` 对应那行。

**反例**：用户说"这支片别用蓝色，太冷"，就把"避免蓝色"写成 `methods/avoid-blue.md`，还配了可检验特征"画面里没有蓝色"。错在第 1 步和第 4 步：把这一次的项目选择当成了跨作品方法（换一支暖调片子，这句就是错的）；而"没有蓝色"不是可检验特征，是一条无法失效的禁令——它不告诉你什么情况下蓝色才是对的。

## 7. 整理与删除

整理不是额外工程，是库还能被读的前提。四个动作的判据见 `references/curation.md`，顺序固定：

1. 两条说同一件事 → 合并，出处并列
2. 三个月没被用过 → 删（删不是失败，是库在正常工作）
3. 某个做法在两支以上不同的片里都成立 → 从 `prompts/`、`lessons.md` 提升成 `methods/` 一张方法卡
4. 一条方法真的失败了 → 不删，转成反例，写回原条目的失效条件或单独列一条

删之前两个确认：它是不是某支片唯一的记录；有没有别的条目或作品文件引用它。

`index.md` 长到一屏读不完（大致 40 行以上）就先整理再写新的。库的价值在"能一次扫完"，不在条数。

## 8. 边界

- 不替用户定审美偏好：偏好由用户自己说，本份只负责把它放对位置。
- 不把方法写成 Skill：值得固化成技能时走 `video-skill-authoring`，库条目退成一句指针。
- 不建数据库、不做状态机、不做全连接依赖图（D-09）：库是手写 Markdown 加一个 `index.md`，没有索引服务。
- 当前作品的方案、镜头、时长归 `video-plan`；证据索引（§1.5）在作品文件夹里，归 `video-review` 与取证工具，不进库。
- 条目字段只在 `docs/编写规范.md` §1.4 定义，本份只用不定义。

**不适用**：用户要的是这一次怎么拍，不是下次怎么用（用 `video-plan`）；用户想把这套做法变成可复用技能（用 `video-skill-authoring`）；用户问的是某几秒到底哪里不对（用 `video-review`）。

## 按需参考

- 要建库、判断这次该读还是该写、三个月没用的条目怎么处置、某条东西该写回哪个文件 → `references/library-rules.md`
- 一条东西写不出可检验特征或反例，要判断是偏好还是方法 → `references/entry-quality.md`
- 出现重复条目、要删一批、要考虑提升成技能 → `references/curation.md`

## 来源与限制

依据：`docs/编写规范.md`（§1.4 库条目、§2 分工表第 12 行、§3—§10）。方法来源见三份参考各自的"依据"，主体是 `resources/research/已确认资产/07-产品与工作流/` 下 07、08、09、10 四份要点（A 级自写，不随包分发）。
未实测：库的三个月清理、合并、提升为技能都只是规则，没有在真实多作品序列上执行过；条目质量判据来自写作时对反例的推演，不是用户反馈校准的结果。**已产出过一次**：2026-11-19 那支 5 分 12 秒科普片结束时按本份规则建出 7 类 8 个文件，但**没有第二支片验证过复用**。
缺口：条目"用过"的判定靠人工核对 `index.md` 与作品文件夹，没有工具支持；库路径跟着工作区走，换工作区就是另一个库，插件不做跨工作区合并。
