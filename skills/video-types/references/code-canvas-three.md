# 画法取舍：Canvas、three、HTML 到帧

> 何时读：已经决定这一镜用代码画，正在选"用哪种代码画"时；或已经画了但不满意——字糊、边缘有锯齿、3D 一面亮一面黑、每帧越来越慢。读它是为了按"这镜要表达什么"选画法，并事先知道每种画法会在哪里翻车。

## 1. 一个前提：先问画面里最不能出错的是什么

| 这一镜最不能出错的是 | 该选 | 理由 |
|---|---|---|
| 字的位置、换行、对齐、排版 | HTML/CSS（DOM 或 SVG 里的文字），3D 只做背景 | 排版引擎替你算字宽、换行、基线；在 Canvas 里手算这些是最容易崩的一类活 |
| 几何形状、线条、图表、参数关系 | SVG 或 Canvas 2D 的矢量绘制 | 坐标可精确到小数、可逆、可只渲任意一帧 |
| 材质、光照、体积、真实空间关系 | three（WebGL）或离线 3D 渲染 | 光与材质是这类引擎唯一不可替代的部分 |
| 大量粒子的密集运动 | Canvas 2D 或着色器 | DOM 节点一多就慢；数量决定了不能走 DOM |
| 干净锐利的最终像素 | 按设备像素比出帧，矢量优先 | 位图放大必糊，矢量与 2× 截图不糊 |

判据的用法：**先定"最不能出错的那一件"，其余部分让位。** 一镜只能有一个主角式的技术选择；想同时拿到"排版准 + 真实光照 + 每秒几百个粒子"，通常意味着这一镜该拆成两镜。

## 2. Canvas 2D

适合：图表、粒子、线条生长、像素风、需要逐像素控制的效果。

- **分辨率要按设备像素比乘。** 画布逻辑尺寸 1920×1080，实际像素按 2× 建，再把绘图上下文缩放回去；不这么做，文字与细线在成片里是糊的，而预览时看不出来。
- **文字排版要自己负责。** 换行、字宽、行高、居中、省略号都得手算。中文尤其危险：手算的字宽与字体真实字宽不一致时，一切对齐都错，而且只在个别字上错，很难发现。
- **没有层级。** 谁后画谁在上面，遮挡关系要自己在代码里排好顺序；这既省事（可精确控制）也危险（顺序错了就是穿帮）。
- **每帧重画整屏。** 元素多时成本线性上升；把静态背景预渲到离屏缓冲，只重画动的部分，是最有效的省法。

## 3. SVG / DOM

适合：讲解图、字形演示、注脚与标签、需要大量文字的场景、要"可读的矢量图"的画面。

- **优点是排版与矢量**：字由排版引擎排，缩放不糊；组与组可以独立变换，做"带引线的标注""逐字揭示"很自然。
- **缺点是节点数与滤镜**：几百个节点还算轻，几千个开始明显慢；大面积模糊、阴影、混合模式是真正的开销来源。
- **出帧要靠浏览器截图**：没有"自带导出"，必须由外部驱动"设到时刻 t → 截一张"。这条路径天然适合帧域纯函数（见 `render-pipeline.md`）。

## 4. HTML 到帧（CSS / DOM 动画 + 截图）

最容易把版式做对的一条路，但有一个必须改掉的习惯：

- **不要"播放"，要"设置"。** 用 CSS 动画自动播放再录屏，会引入掉帧、不同步、加载时序问题，而且不能回退到任意时刻。正确做法是把动画的状态变成时间的函数：给定 t，算出每个元素的位移/透明度/进度，再截图。CSS 的动画对象可以被外部设到指定进度，这是可 scrub 的关键；自己写 `setTimeout` 串起来的"时间线"则不可 scrub。
- **首帧与资源**：字体、图片、着色器编译都可能让第一帧与后面不同。取帧前显式等待就绪，并且把"没就绪就取帧"当成错误而不是常态。
- **层叠与裁切**：溢出裁切的容器会让"字被裁一半"看起来像设计；验收时单独查（见 `code-visual-review.md`）。

## 5. three / WebGL

适合：真实光照下的产品、空间关系本身就是要讲的内容（转盘看结构、剖面看层次）、需要景深与体积感的一镜。

- **文字别在 3D 里画。** 3D 场景里的文字要么变成贴图（放大必糊、字宽由贴图决定），要么变成网格（排版要自己写）。通行做法是：3D 渲场景，文字与标签用 HTML 叠在上面，按投影坐标跟随。这样排版仍归排版引擎。
- **叠加层要对齐，就要每帧更新矩阵。** 把 3D 点投到屏幕坐标前，必须让相机矩阵是当前帧的；漏更新会用到上一帧的矩阵，表现在"跳着看某一时刻时标签跑位"，而顺序播放时看不出来。
- **无头环境要显式开 WebGL**，否则静默降级成空白或低质量，且不报错。
- **成本不可忽略地随设备变**。同一场景在开发机与目标机上差一档很常见；先量再承诺。
- **透明与排序**：玻璃、光锥、半透明片是排序与阴影贴图的高发区。有资产记录过：只关掉"投射阴影"不够，接收阴影的网格仍会被画进阴影图，必须两样都关，并把透明体排除在环境光遮蔽之外。
- **确定性只到同机**：GPU、驱动、精度不同，抗锯齿与浮点结果就不同。

## 6. 离线 3D 渲染（Blender 一类）

只有一种情况值得走：这一镜必须是真 3D，且要的质感光栅化引擎给不了。代价是管线重（另装工具、另一套时间与输出）、返修慢、与其余镜的拼装方式不同。`mg-styles-15` 的 15 支里只有 1 支走这条路，其余全是网页代码出帧——比例本身就是信息。

## 7. 混用规则

- 一镜之内可以混，但要按"谁负责什么"分层，并且**层与层只在时间上对齐，不在数据上互改**：3D 负责空间，DOM 负责文字，Canvas 负责粒子。
- 混用会放大确定性风险：每多一层，就多一个"没就绪就取帧"的机会。层数越多，冷渲/热渲对比越必须做。
- 同一支片里画法不要超过两种。画法一多，观众看到的是"每镜换一种拼贴"，不是风格（`mg-styles-15` 与 `huashu` 都把这个当缺陷记过：前者靠"一支片一个网页、一种风格"约束，后者把"每镜换一种画风的拼贴"写进六种做坏方式）。

## 8. 性能上限（都是一台机器上的实测，不是定律）

来自一份 3D 图解的实测预算，用来建立量级感，不要当验收阈值：

| 量 | 轻量图形 | 密集图形 |
|---|---|---|
| "重量"合计（以单个可动棱柱为 1 计） | 约 50 | 约 230 |
| 每帧 CPU（Node 侧计算） | ≤ 2 ms | ≤ 7 ms |
| 浏览器主线程任务（1440 宽、2 倍像素比） | ≤ 6 ms | ≤ 13 ms（按 60fps） |
| 移动端（390 宽、3 倍像素比、4 倍 CPU 降速） | ≤ 16 ms | ≤ 33 ms（按 30fps） |

同源的相对成本（同样以棱柱为 1）：竖直旋转的固定件约 0.5、普通棱柱 1、管段 2—3、旋转体约 25、带平切的球 8—10。**带平切的球一个顶九个棱柱**，这是"看起来只是加了个圆头"却突然变慢的典型原因。

三条可迁移的做法：

1. 细节（点、环、螺栓）当"细节"画，不当零件；静态杂物当静态图，不进每帧循环。
2. 每帧先量时间，超了就按帧率降半速出（运动按时间算，所以慢下来不变形），恢复了再回全速。
3. 大图先减采样：小于某个像素尺寸的圆环、端盖少采样，肉眼看不出来。

## 9. 已知限制（原文写了什么就说什么）

- 有的 3D 绘制方案**只支持凸体**，凹形要拆成凸块；平面交叉处靠短暂淡化过渡（约 ±0.035 的分数，折算约 8° 转角），转角快了会看到一闪。
- 它**不会自动切分**会穿模的部件，只能报错并给建议平面。
- 手机端目标是 30fps 而不是 60；一个 380 部件的压力场景实测约 20fps（1440 宽），移动端 13—15fps。
- 被借来做实时视觉的工具可能自标"实验性、仅 Chrome + WebGL"，参数随时间的函数化思想可以借，稳定性不能借。
- 一套参数化片段模板通常有单段时长上限（某套是 8 秒）。这是模板的界限，换模板要重新确认。
