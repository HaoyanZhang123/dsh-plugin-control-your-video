# 代码画面：该不该用、两道门、怎么验收

> 何时读：这一镜打算用代码/程序化出画面，或代码画面出了问题（不可复现、字变样、渲得慢）。读它是为了在动手前把时间来源与确定性定死，并在交付前能判"这镜过了"。

## 一、该不该用代码画

不是"能不能"，是"该不该"。只回答一个问题：这一镜要观众**看懂**什么。

| 这一镜要观众看懂的 | 判据 |
|---|---|
| 结构、顺序、数量、比例、参数关系 | 画面能被算出来，且算出来比拍出来更准 |
| 一个过程怎么发生（长出来、拆开、对上） | 变化本身是信息，不是修饰 |
| 真实的人、现场、材质与光 | 观众判的是"像不像真的"，几何再准也过不了 |
| 情绪、微表情、手感细节 | 细节里的不确定给不出来 |
| 已经有实拍或截图素材的段落 | 素材就是主画面，代码只该做标注与运镜 |

三条硬规则：

1. **写"做法＝代码"之前，先能说出这一镜"算的是什么"。** 说不出算的是什么，说明这一镜要的是质感——只是把"我不会拍"说成了"我用代码"。
2. **替换测试**：把这镜的代码画面换成一张精确的静态示意图，信息还在不在？还在，你要的是图解，不需要整条出帧管线；全丢了，才说明代码在承担"过程"。
3. **不许因为代码容易就全片代码画。** 识别方法：数一遍"做法"里代码的占比；过半时逐镜回读画面列——凡是写着真人、现场、一只手、一件实物、一张截图素材的镜，做法就不该是代码。这类镜出去（实拍素材或生成模型），不是留在代码里硬画。

**不要为了迁就代码改镜头。** 把"手持特写"改成"正面不动"，是把用户否掉的东西当方案交上去。

## 二、第一道门：时间来源

三选一，定了才能写第一行动画。中途换等于重做。

| 时间来源 | 什么时候用 | 代价 |
|---|---|---|
| **帧域纯函数** | 要交付、要可复现、要能跳到任意时刻 | 写起来最费脑：每个状态都得能从 `t` 算出来 |
| **弹簧积分** | 要重量与回弹 | **不是时间纯函数**，24/30/60fps 同参数不同形 |
| **曲线映射** | 语义清楚、快出效果 | 绑实现，换引擎要重做 |

判据是"能不能跳到任意时刻再往回"。要交付的片子一律用帧域纯函数；弹簧只用于不需要跨帧率一致、不需要 scrub 的场合。

**锚点从外面拿，不要自己数拍。** 要跟剪辑时间对上的动效（滚动与键盘声同步），把秒数当参数从时间线传进来；在代码里数拍子，等于维护第二份时间轴。

## 三、第二道门：确定性

要求只有一条：**同一工程两次渲染，同一时刻逐像素一致**。验法：冷渲一次、热渲一次，分开比。

破坏它的清单（按发生频率排）：

1. **运行期从 CDN 拉库和字体**——硬杀手，网断了画面就变。
2. **字体回退**：缺字静默换系统字体，代码里看不出异常。
3. **没种子的随机**。
4. **读系统时钟**（`Date.now()`、`performance.now()` 进画面）。
5. **逐帧累加状态**（`x += v` 而不是 `x = f(t)`）。
6. **资源没就绪就取帧**（字体、图片、纹理加载完成前渲染）。
7. **跨机 GPU 差异**（着色器精度、抗锯齿、颜色管理）。

两道门没过就别调节奏与美观——那时做出的"好看"不可复现，等于白做。

## 四、画法怎么选

先定"这一镜最不能出错的是什么"，再选：

| 最不能出错的是 | 用 |
|---|---|
| 排版、字与行的精确控制 | HTML/CSS + 浏览器出帧 |
| 几何、图表、图标 | SVG（静态精度）或 Canvas（大量元素） |
| 材质、空间、光照 | three.js / WebGL；**文字仍用 HTML 叠层**，不要用 3D 文本 |
| 后期效果（景深、bloom、颗粒） | 先渲干净再后期，不塞进出帧循环 |

**为什么文字单独一层**：3D 里的文字会跟着透视变形、分辨率不稳、字体渲染跨机不一致。把文字留在 DOM 层，改字不用重渲整个场景。

## 五、字体

第一翻车项。做法：

1. 画面里每个字（含数字、标点、符号）都必须在该字体文件里。
2. 用子集化工具按最终文案生成字体；**改文案就重做子集**。
3. 跨机承诺之前，先在同一台机器上核一遍字宽与排版没有变化。
4. 记录字体名称、版本、来源与许可（能不能随工程分发是另一件事，见 `video-release`）。

## 六、验收：怎么判这一镜过了

- **逐帧证据**：每镜至少起点、动作中点、落点、镜末四张；带转场的另加 3 张；文件名带镜号与秒数。
- **跳帧比对**：单渲第 3.2 秒那一帧，与顺放到该帧比对。不一致说明实现里存了上一帧状态（第二道门破了）。
- **每镜一行结论**：看了哪几处 → 量到什么 → 过／黄／红 → 哪项没看。
- **一页交付说明**：时间来源、确定性怎么验的、性能数字、用了哪几套字体与能否分发、已知限制。

验收清单的完整版见 `code-visual-review.md`。

## 七、工程组织

- **一镜一文件**：同镜号一个视频文件，全片同宽高同帧率，便于硬切拼接。
- **中间帧序列留在工作目录**，交付的是组装好的成片（见 `video-types` §8）。
- **渲染脚本要能一把重来**：一条命令从源码到成片。做不到的项目，改第三镜那次就会出事。
- **性能预算**：单帧渲染时间 × 总帧数 = 迭代成本。超过"今晚能试三个版本"的量级，就要降精度、拆镜头或换路线。

## 八、失败模式与对应改法

| 现象 | 常见原因 | 改法 |
|---|---|---|
| 两次渲染不一样 | 随机/时钟/资源未就绪 | 固定种子、去掉时钟、等资源就绪 |
| 换台机器字变了 | 字体回退 | 子集化并内嵌，核字宽 |
| 顺放正常，跳帧不对 | 逐帧累加状态 | 改成 `f(t)` |
| 越渲越慢、内存涨 | 每帧新建对象/不释放纹理 | 复用、显式 dispose |
| 视频里字发虚 | 文字进了 3D 层或被缩放 | 文字留 DOM 层，按整数倍缩放 |
| 边缘锯齿 | 出帧分辨率低于交付分辨率 | 提高渲染尺寸再缩 |
| 卡顿但导出的片子流畅 | 预览页性能，不是成片问题 | 分开判：预览卡不影响成片 |

**未验证**：本文的性能判断与"两次渲染逐像素一致"来自工程常识与资产作者的实测记录，本包没有在真实项目上跑过完整的代码出帧管线；具体引擎的默认行为（尤其 three.js 的精度与颜色管理）需按当前版本文档核。
