# 出帧管线：时间来源、确定性、分辨率与可复现

> 何时读：已经决定这一镜用代码画，并且这个画面要交出去给人看（不只是一张预览静帧）时；或同一工程两次渲染对不上、换一台机器画面就变了、字体或帧率出问题时。读它是为了在写第一行动画代码之前，把时间来源、帧率、依赖和字体定死，出问题时有地方可查。

## 1. 时间来源只有三类，先选再写

| 类型 | 画面怎么算 | 它换来什么 | 它放弃什么 |
|---|---|---|---|
| 帧域纯函数 | 位置 = f(t)，给定 t 直接算出那一刻的全部几何 | 可 scrub、可逆、跨次渲染一致、可只渲任意一帧 | 没有"惯性"，重量要手写进曲线里 |
| 弹簧积分 | 每帧从上一帧位置和速度推进一步（质量、阻尼、刚度） | 有重量、有回弹，参数一改手感就变 | 跨帧率不一致、不可直接 scrub、依赖前序帧 |
| rate function | 把 0—1 的进度用一条语义曲线（回弹、弹性、颤抖）映射 | 语义清楚，曲线即描述 | 曲线与实现绑定，换渲染器就可能还原不出同一条 |

判据，按顺序：

1. **要交付成片，默认帧域纯函数。** 因为验收、返修、补渲一帧都要求"给时间就能拿到那一刻"；弹簧做不到这点。
2. **只在"必须有重量"的地方用弹簧**，并且当场接受代价：同一工程 24fps 与 30fps 出来的动作不一样。定下帧率之后不再改。
3. **rate function 只在自己完全掌控的渲染器里用**。它的可复现性来自"这条曲线是我的代码"，不来自引擎名称。
4. **不要在同一镜里混三种。** 一部分纯函数、一部分弹簧，scrub 到中途时两者对不上，而人对"对不上"的容忍度远低于对"不够顺"的容忍度。

### "定死时间来源"具体是哪四件事

- 时间基准只有一个：秒或帧号选一个，换算固定（帧号除帧率得秒），中途不改帧率。
- 所有运动算的是**镜头局部时间**（当前 t 减本镜起点），不跨镜共用一根全局时钟。否则剪掉一镜，后面全歪。
- 元素**不存状态**。不写"上一帧位置加位移"，位置必须是 t 的函数；判据：任意跳着渲一帧，画面必须和顺放时那一帧一样。
- 声音、字幕、节拍点这类**锚点来自外部时间线**，代码只把它们当参数读进来，不自己数拍子。

四条都成立才叫"时间来源定了"。写的时候才发现要换来源，等于动画重做——所以这一条必须在动手前答。

## 2. 确定性：可验证，不是感觉

要求写成一句话：**同一工程、同一参数、同一机器，两次渲染的同一时刻逐像素一致。**

怎么验：

- **冷渲 + 热渲各一次**，同一时刻取帧、逐像素比对。必须分开做，因为热渲会吃到缓存、编译好的着色器、已解码的贴图，冷渲不会。只比一次等于没测。
- 比对要在**转场处**和**段中静止处**都做。静止处一样但转场处崩，是最常见的漏检。
- 交付规格里的"逐像素一致"只对**原始帧**成立。编码成 mp4 之后，编码器与多线程会让两次输出不同；这一步放宽到"帧数一致、时长一致、抽帧目视一致"，不要承诺文件哈希相同。

会破坏确定性的东西，逐条对：

| 来源 | 表现 | 处置 |
|---|---|---|
| 随机数没有种子 | 每次粒子/抖动/笔触不同 | 用带种子的确定性散列（输入序号→[0,1)），不用系统随机 |
| 读系统时钟 | 动画起点随加载时刻漂 | 时间只从传入的 t 来 |
| 异步加载未完成就取帧 | 图/字体没到，一帧空一帧有 | 取帧前显式等资源就绪；启动失败要直接报错退出，不要静默继续 |
| 系统字体回退 | 换机器字形全变 | 见第 5 节 |
| 浮点累积 | 长时间运行后位置漂移 | 位置从 t 一次算出，不逐帧累加 |
| GPU / 驱动差异 | 同工程换显卡抗锯齿、混合、精度不同 | 只承诺同机可复现；跨机要单独验 |
| 网络依赖 | 离线换环境就缺库或换版本 | 运行期一律不访问网络 |
| 状态残留 | 换一镜后上一镜的残留还在 | 每镜从干净状态起 |

**真实反例**：`lanshu` 的风格化路线，GSAP 与 three 从 jsDelivr 拉，字体子集从 Google Fonts / jsDelivr 拉（其 `THIRD_PARTY.md` 自己写明）。这类工程在网络通、CDN 稳定时看起来完全正常，但离线、换网络、CDN 换版本之后，同一份源码渲不出同一支片。它把版本写在依赖清单里是诚实的，但这不改变"运行期依赖 CDN 就不能承诺离线可复现"。

对照做法：`huashu-art-motion` 把引擎整份复制进项目（`scripts/engine`），字体是工程内自带的 woff 子集，于是"同一时刻渲两次逐像素一致"能被当成一条可执行的自检项写进流程。

## 3. 分辨率与帧率

三个数字必须分开命名，混用是返工源头：

| 数字 | 谁定 | 作用 |
|---|---|---|
| 交付帧率 | 平台与片型 | 成片规格。一镜一文件、全片同宽高同帧率，才好在剪辑里硬切拼 |
| 验收帧率 | 你抽帧看画面的密度 | 通常高于"够用"，用于发现跳变与闪烁 |
| 分析帧率 | 门禁脚本的测量密度 | 常远低于交付帧率（降采样到 12fps、320 宽这类），只用来量趋势，不能用来判画面好坏 |

- 画布尺寸与**设备像素比**是两件事。按 1× 截图出来的字发虚，放大看边缘全是糊的；按 2× 出再交付才锐。设备像素比要写进工程参数，不靠"截图工具默认值"。
- 竖屏不是重做：同一条管线换宽高即可，但**安全区要重算**——横屏算好的边距搬到竖屏会溢出，字幕带位置也变。
- 规格先写死再动手：宽、高、帧率、时长。时长精确到 0.001 秒这种要求只能靠"出帧序列 + 编码时指定帧数与帧率"来保证，不能靠动画自己"大概停在 10 秒"。
- 时长上限由片段模板决定，不由想象力决定：`huashu-art-motion` 的镜头表检查把"同一个参数化片段超过 8 秒"判为红灯。这是它那套模板的实测界限，不是引擎规律——但结论可迁移：**先确认当前模板一段撑多长，超了就拆镜**，别硬撑。

## 4. 离线可复现

一个工程能不能离线重跑，取决于四层都本地化：

1. 运行时（浏览器 / Node / Python）版本；
2. 渲染驱动（无头浏览器、截图工具）；
3. 编码器（ffmpeg 及其参数）；
4. 素材与字体。

- **锁版本，然后承认锁不住的部分。** `mg-styles-15` 作者自述：音轨脚本在同一环境重跑是确定的，但按它给的版本重跑，15 支里只有 4 支与成片逐位一致，另外 11 支"某些地方不同"，怀疑来自数值库变化。所以"锁定版本 = 完全复现"这句话不能写；能写的是"锁定版本后差异局限在可接受范围，实测记录在此"。
- **资源路径要有一个确定的根。** 页面里写绝对的站内路径（`/assets/...`）时，必须"以工程根启动本地服务"才能打开；直接双击 html 会 404，而 404 的图在画面上表现成空块，很容易被当成设计。这一条 `mg-styles-15` 的说明里明确要求了。
- **无头浏览器要显式开 WebGL**。不开的时候着色器静默降级或整块不画，画面看起来"就是这样"，其实是没渲。有一份资产（`anatomy` 的验证指南）专门提供"关掉 WebGL 再跑一遍"的检查，用来确认降级路径不崩——这是一个值得照搬的动作：**关掉某一层再跑一次，看会发生什么**。
- 运行期禁止访问网络。构建期取依赖要记录版本与出处，写进交付说明。

## 5. 字体：最容易翻车的一环

三个已经写明的坑，中文尤其严重：

1. **缺字形会静默回退到系统字体**，换一台机器字形完全不同，而代码里看不出任何异常（`huashu` 的字体子集脚本开篇就写这句）。它的对策是引擎启动时校验要用的字，缺了就打错误日志并让验收失败。
2. **子集化会缺字**。子集只含"当时用到的字"，改一句文案就要重跑子集，包括从 JS 里写出来的字（`lanshu` 的坑清单里同样记了这一条）。
3. **跨机器字宽变化**会让换行、居中、右对齐一起崩。同一字体不同版本，或一个字形被别的字库借来补，字宽都可能不同（`lanshu` 记录过：某字体的"回"字内框是实心方块，只能从另一套字库借这一个字形）。

检查项，交付前逐条过：

- 画面里出现的每一个字（含数字、单位、符号）都在字体文件里；缺了就补子集，不靠回退。
- 从 JS 里动态写出来的字也扫进去了。
- 字体在第一次绘制前就加载完成；晚加载 + 阻塞式显示 = 前几秒的字是空的。
- 中文行高不要压到 1.0：中文字身框会比行高高，行高太小会互相压住或顶到上一行（同一份坑清单有记）。
- 全角空格的宽度要单独查，有字体把它做成 0 宽（这是真实存在过的字库缺陷）。
- 字体许可与分发：有的字体允许用、不允许转换后再分发，只能本地自己生成子集；因此**字体文件常常不随工程发布**（`mg-styles-15` 就没放字体文件，缺字体时浏览器回退，字形与成片不一致——它自己在说明里标了这个缺口）。交付说明里写明：用了哪几套字、从哪来、能不能随包分发。

## 6. 出片与组装

- 出帧序列之后编码，是"帧 → 时间"的唯一可靠路径。渲染时由动画自己播、再录屏，会引入掉帧与不同步。
- 一镜一个文件、同宽高同帧率，拼接才是硬切；要加转场就必须**整片模式一次出**，不能逐镜出完再拼（`huashu` 的流程明确分开这两条路）。
- **转场必须单独冒烟渲。** 逐段取帧时只调段内渲染，转场代码一次都不会执行，所以"转场崩了、逐段验收全绿"是真实发生过的（同一资产的记录）。做法：在有转场的段上，按 1/4、1/2、3/4 进度各渲一张整帧，把页面报错计入结果。
- 取帧要避开镜头冲击：段首那零点几秒是运镜最猛的地方，用它判断"有没有内容"会误判。把测量起点往后挪，或按动作表把镜头事件单独标注出来。

## 7. 已知限制（照实转述，不淡化）

- 无头 Chromium 的 GPU、抗锯齿、精度与真机不同。同机可复现不等于跨机一致。
- 参数化片段模板普遍有单段时长上限（某套是 8 秒）。超过就拆，不要靠改参数硬撑。
- 手机端预算按 30fps 算，不是 60fps（`anatomy` 的 3D 参考自己这么写）。
- 有引擎把自己标为实验性、只支持 Chrome + WebGL（`Hydra` 的 README）。这类工具可以借思想，不能当生产底座承诺。
- 编码后的 mp4 不能被"逐像素一致"这条要求覆盖。
