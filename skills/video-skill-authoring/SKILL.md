# 技能创作：把做法变成下次还会做的判断

Skill 是**可选指示**：模型先看到目录里的一行名字和一句描述，觉得对才加载正文。它不授予工具、不产生权限、不是会话事件、不是记忆。写 Skill 只有一个目标——让没参与这次的人，被触发之后做出同样的判断。

## 1. 先判断该不该做成 Skill

四问。前三问是拆分判据，第四问是本份特有的，也最常被跳过：

| 问 | 不过关的样子 |
|---|---|
| 用户会不会直接这么说？ | 只有"走到流程第 5 步"才用得上 → 并进已有 Skill 当一节 |
| 脱离完整流程还能独立用吗？ | 每次都要先有 intent 和 plan 才有意义 → 它属于那两份 |
| 正文能 150 行说清吗？ | 要靠六份参考才立得住 → 先收窄成一条判断链，别造大 Skill |
| **这个做法模型本来就会吗？** | "要好看""注意节奏""先理解需求"——会，所以不值一份 Skill |

第四问的判据：删掉这份 Skill，模型的行为会变差吗？不会就是空文档。活下来的专业增量必须是做过的人才说得出的判断——"画面自己在动时镜头就该停"能活，"运镜要有目的"不能。

## 2. 不把方法写成能力假设

最常见的坏句子是"可以调用 XX 模型生成""用工具测量后判断"。Skill 正文不挂工具，写了也不会出现那个能力，只会让模型以为自己能。正确写法是先查当前可用、查不到就降级："有真实帧就看帧；没有就只说假设，并写清缺什么。"

## 3. 方法 / 偏好 / 一次运气

提炼前先分三堆，去处完全不同：

| 类型 | 判据 | 去处 |
|---|---|---|
| 这次项目的偏好 | 换个客户、换个题材就不成立（"这个品牌不要蓝紫"） | `preferences.md`，不做 Skill |
| 这个人偶然选对了 | 说得出结果，说不出为什么；换个输入就不知道怎么办 | 不提炼，最多进 `lessons.md` |
| 下次还能用的方法 | 说得出适用条件、举得出反例、能预测没见过的输入 | 先记库条目；成套的才做 Skill |

分水岭是"能说出为什么"。只有结果没有理由的，写进 Skill 就是把运气固化成规则。

## 4. 写成可检验的形式

方法的三个部件：**可检验特征**（怎么看出它在用）＋**适用条件**（什么片型、什么工具下成立）＋**反例**（什么时候不成立）。写不出反例，说明还没想清。

这和 video-library 的条目质量是同一把尺，分工不同：库记**一条**可检验的东西；Skill 承载**一整套**判断——先看什么、分几类、每类怎么处置、边界在哪。一条库条目反复被读，说明它够稳，可以进 Skill；但只有它带着一串判断顺序时才是 Skill，单条事实留在库里。

一个 Skill 只承担**一次可独立验收的判断单元**。把三件互不相干的事塞进一份，等于每个触发都要付另外两件事的阅读成本。

## 5. 写在哪一层，代价不同

| 去处 | 谁看得见 | 代价 |
|---|---|---|
| 包内 `skills/<name>/`，经 `customSkillDirs` 装配 | 只有本 preset | 新增目录要改 patch 并重装；产品方法放这 |
| `<工作区>/.dsh/skills/<name>/` | 该工作区所有会话 | 自动发现、不用改 patch；只在这台机器这个项目里 |
| `$DSH_HOME/skills/` | **所有 preset** | 会泄漏到无关会话，产品内容严禁放这里 |

用户自己写的技能走第二行，写完开新会话就能看到。要跟产品一起分发，才走第一行。

## 6. 触发面只有一个：description

目录消息里只有 `name` 和 `description`，正文在**触发之后**才进上下文。由此三条：

- "何时使用本 Skill"写进正文等于没写——那时触发早就发生了。它属于 `description`，三段：做什么／何时用／不适用。
- 负向边界要往前放；字符上限与"首个不适用位置"以 `docs/编写规范.md` §4 为准，并点名替代技能。
- 加载结果只给**资源基址**，不枚举 `references/`。正文不写"什么条件下读哪份"，参考文件在模型眼里等于不存在。

正文只放四类：判断顺序、决策规则、产出格式、边界与指针。字段表、rank、命令、模型清单、案例长文一律进 references。

## 7. 改完什么要重来一遍

| 改了什么 | 要做什么 |
|---|---|
| 正文 | 立刻生效；不产生目录消息，老会话也能用 |
| frontmatter，尤其 `description` | 刷新目录；要新开会话才看得到新的目录 |
| 目录结构、patch、新增技能 | 重装 + **新开会话**；老会话保持启动版本 |
| `references/`、`scripts/`、`assets/` 内容 | 正在进行的会话不会重新发现；要新开会话再验证 |

验证只看一件事：**新会话的技能目录里有没有那个名字**。不要从模型说"我没看到"反推原因，那是最不可靠的证据源；也不要拿日志当证据。

## 8. 验证四层不能互相代替

| 层 | 证明什么 | 不能证明 |
|---|---|---|
| 结构校验 | 名字、frontmatter、行数、参考头两行合规 | 内容有用 |
| 静态评审 | 有专业增量、无空话、示例具体 | 模型会照做 |
| 隔离的新会话任务 | 会加载、行为真的变了 | 作品好不好 |
| 真实作品 + 用户看 | 这次能用 | 普遍有效 |

顺序不能跳：前三层都过了才能说"这份技能被验证过"，四层都过了也只对这次的作品成立。做完前两层就说"技能可用了"，是假结论。

## 9. 产出格式

1. `skills/<name>/SKILL.md`：≤150 行，五节骨架——判断顺序／决策规则／产出格式／边界与指针／来源与限制。
2. `references/*.md`：一主题一份，头两行固定 `# 中文标题`＋空行＋`> 何时读：<条件>。读它是为了<解决什么判断>。` 没有真内容就不建。
3. 正文"按需参考"一节：每条 `触发条件 → 文件名`，与上面每份的头两行逐条对得上。
4. 交付时说清三件事：放哪一层、哪些改动要新开会话、下一步用哪个任务验证。不建目录、不建占位文件。

## 10. 三个判断示例

**1. 用户说："这套做法挺好，记成技能吧。"**
→ 你这样判断：先问是哪一套。若他说的是"这次客户不接受蓝紫渐变"，那是偏好，进 `preferences.md`；若他说的是"字幕压脸的三种成因和分别怎么改"，那有判断顺序、有反例、换片型也成立，够一份 Skill。
→ 所以你这样做：先记一条库条目（一句话＋可检验特征＋适用条件＋反例），问他下次还要不要这套判断；要，再按 §9 写成 `video-edit` 的一节或独立技能，并写清放哪一层。

**2. 用户说："我自己写的技能放在 `.dsh/skills` 里了，怎么没生效？"**
→ 你这样判断：按机制顺序查——目录名与 `name` 是否逐字一致、frontmatter 是否合法（尤其 invocation 键别写驼峰，写了整条被丢弃）、是否用了老会话、是否被更高 rank 的同名技能盖住。不是先怀疑模型没看见。
→ 所以你这样做：让他新开一个会话，看技能目录里有没有那个名字；名字在但没触发，改 `description` 的触发面，不是改正文。

**3. 用户说："这个技能好像没触发，正文里明明写了什么时候用。"**
→ 你这样判断：正文里写"何时使用"是加载之后才看得见的，晚于触发决定。触发面只有 `description`。
→ 所以你这样做：把那句"何时使用"从正文搬到 `description` 第二段，用用户的原话；负向边界提到前 220 字符内并点名替代技能；然后新开会话用一句真实的话试，不提技能名。

**反例（真实会犯）**：把"这次客户不要蓝紫"写成一份《配色 Skill》。错在哪一步：错在 §3 没分堆——把一次项目偏好当成方法，还写进了正文。后果有两个：换个客户，这份技能会把可用色砍掉一半；每个触发它的人都先付一段无关约束的阅读成本。正确处置是写进 `preferences.md` 一行，Skill 里只留判断——"这类片子里蓝紫会抢主体，因为主体是暖光下的实物"。

## 11. 不适用

- 用户只想"记住这次喜欢什么"——那是 video-library 的 `preferences.md`，不是 Skill。
- 用户想"让模型能调用某个工具或模型"——那是装配与工具的事（用 dsh-doc），Skill 文字不授予能力。
- 要判断本包 13 份各自的内容对不对——各归其份；本份只管"怎么写、放哪、怎么验"。
- 方法还没成形（只有一次结果、说不清为什么）——不写 Skill，先记库条目并标"待验证"。

## 按需参考

- 用户刚做完一次任务说"以后都这么做"，要分清哪部分是方法、哪部分只是这次的偏好或运气 → `references/method-extraction.md`
- 要新建或移动一份技能、要决定放哪一层，或"技能没出现/没触发"要定位原因 → `references/dsh-conventions.md`
- 一份技能写完或改完 `description`，要回答"它到底有没有用" → `references/verify-skill.md`
