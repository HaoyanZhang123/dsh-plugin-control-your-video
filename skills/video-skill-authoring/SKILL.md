# 技能创作与知识治理

Skill 是**可选指示**：模型先看到目录里的一行名字和一句描述，觉得对才加载正文。它不授予工具、不产生权限、不是记忆。

写 Skill 只有一个目标——**让没参与这次的人，被触发之后做出同样的判断**。本文只管本包特有的部分：什么值得沉淀、怎么写得能被触发、改完怎么验。通用写法与 DSH 机制（frontmatter 字段、rank、装配、watch）查宿主自带的 `skill-creator` 与 `dsh-doc`，本份不复述。

## 1. 四问：该不该做成 Skill

前三问决定拆分，第四问最常被跳过：

| 问 | 不过关的样子 |
|---|---|
| 用户会不会直接这么说？ | 只有"走到流程第 5 步"才用得上 → 并进已有 Skill 当一节 |
| 脱离完整流程还能独立用吗？ | 每次都要先有意图和方案才有意义 → 它属于那两份 |
| 能不能收窄成一条判断链？ | 要靠六份参考才立得住 → 先收窄，别造大 Skill |
| **这个做法模型本来就会吗？** | "要好看""注意节奏""先理解需求"——会，所以不值一份 Skill |

第四问的判据：删掉这份 Skill，模型的行为会变差吗？不会就是空文档。活下来的专业增量必须是做过的人才说得出的判断——"画面自己在动时镜头就该停"能活，"运镜要有目的"不能。

## 2. 方法 / 偏好 / 一次运气

提炼前先分三堆，去处完全不同：

| 类型 | 判据 | 去处 |
|---|---|---|
| 这次项目的偏好 | 换个客户、换个题材就不成立（"这个品牌不要蓝紫"） | 偏好记录，不做 Skill |
| 这个人偶然选对了 | 说得出结果，说不出为什么；换个输入就不知道怎么办 | 不提炼，最多标"待验证" |
| 下次还能用的方法 | 说得出适用条件、举得出反例、能预测没见过的输入 | 先记库条目；成套的才做 Skill |

分水岭是"能说出为什么"。只有结果没有理由的，写进 Skill 就是把运气固化成规则。

## 3. 方法的三个部件

**可检验特征**（怎么看出它在用）＋**适用条件**（什么片型、什么工具下成立）＋**反例**（什么时候不成立）。写不出反例，说明还没想清。

一个 Skill 承担**一次可独立验收的判断单元**。把三件互不相干的事塞进一份，等于每次触发都要付另外两件的阅读成本。

数值尤其要小心：媒体尺寸、字号、运动幅度、节奏阈值都随片型、画幅、平台变。写进知识里的每个数，都要能回答"它在什么条件下成立、失效时什么样"；写不出条件的，不要写成门槛。

## 4. 触发面只有一个：description

目录消息里只有 `name` 和 `description`，正文在**触发之后**才进上下文。由此三条：

- "何时使用本 Skill"写进正文等于没写——那时触发早就发生了。它属于 `description`：**做什么 / 何时用（用用户的原话）/ 不适用并点名替代**。
- 负向边界要往前放；太长会被截断，关键触发词与边界不能放在最后。
- **加载结果只给资源基址，不枚举 `references/`。** 正文不写"什么条件下读哪份"，参考文件在模型眼里等于不存在。

正文只放判断：按什么顺序看、分几类、每类怎么处置、边界在哪、什么条件下读哪份参考。字段表、命令、模型清单、长案例进 `references/`。

## 5. references 的写法

- 一主题一份，文件名用小写字母、数字与连字符（`motion-diagnosis.md`），**不能再分子目录**——读取接口只认 `skills/<name>/references/<file>.md` 这一层。
- 头两行写清"何时读、读它是为了什么"，正文里有一张对应的索引表。**两边要能对上**，否则没人会去读。
- 没有真内容就不建文件。一份只有标题的参考比没有更糟：它会让索引看起来齐了。

## 6. 改完什么要重来一遍

| 改了什么 | 要做什么 |
|---|---|
| 正文 | 立刻生效；不产生目录消息，老会话也能用 |
| frontmatter，尤其 `description` | 刷新目录；**要新开会话**才看得到 |
| 目录结构、patch、新增或删除技能 | 重装 + **新开会话**；老会话保持启动版本 |
| `references/` 内容 | 正在进行的会话不会重新发现；要新开会话再验证 |

验证只看一件事：**新会话的技能目录里有没有那个名字**。不要从模型说"我没看到"反推原因，那是最不可靠的证据源。

## 7. 验证四层不能互相代替

| 层 | 证明什么 | 不能证明 |
|---|---|---|
| 结构校验 | 名字、frontmatter、路径、参考能被读到 | 内容有用 |
| 静态评审 | 有专业增量、无空话、示例具体 | 模型会照做 |
| 隔离的新会话任务 | 会加载、行为真的变了 | 作品好不好 |
| 真实作品 + 用户看 | 这次能用 | 普遍有效 |

做完前两层就说"技能可用了"，是假结论。四层都过了也只对这次的作品成立。

## 8. 不适用

- 用户只想"记住这次喜欢什么"——那是偏好与经验库，走 `video-library`。
- 用户想"让模型能调用某个工具或模型"——那是装配与工具的事（`dsh-doc`），Skill 文字不授予能力。
- 方法还没成形（只有一次结果、说不清为什么）——不写 Skill，先记条目并标"待验证"。
- 要判断本包各份 Skill 的内容对不对——各归其份；本份只管"该不该写、怎么写能被找到、怎么验"。
