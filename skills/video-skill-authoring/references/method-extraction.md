# 从一次任务里提炼方法

> 何时读：用户刚做完一支片或一轮修改，说"以后都这么做""把这套记下来"时。读它是为了分清哪一部分是下次还能用的方法，哪一部分只是这次的偏好、或一次碰巧选对。

## 1. 先分三堆，再谈写法

一次真实的活儿结束后，能被写下来的东西有三种，混在一起写就会把运气固化成规则：

| 类型 | 当场怎么认 | 去处 |
|---|---|---|
| 项目偏好 | 换个客户、换个题材就不成立。"这个品牌不用蓝紫""这条片不要女声" | `preferences.md` 一行，不做方法 |
| 一次运气 | 结果对，但说不出为什么；换个输入就不知道怎么办 | 最多进 `lessons.md`，标"一次观察" |
| 方法 | 说得出为什么、说得出什么条件下成立、说得出什么时候失效 | 先记库条目；成套的做成 Skill |

分水岭只有一个：**能不能说出"为什么"**。说不出的先别写进方法区——写进去以后没人敢改，也没人能用对。

## 2. 从"改了什么"倒推"为什么改"

方法不在成片里，在修改记录里。最有效的原料是修改单第 4 项（属于谁的问题）和第 6 项（改完怎么验）：

- 用户说"字幕压脸了"，你判断是执行问题（安全区没算），不是创作问题 → 这条背后有判断链：**先分问题归属，再决定改哪一层**。
- 用户说"太快了"，你发现不是时长短，是每镜同一个动作 → 背后是：**节奏问题先看动作是否重复，再谈时长**。

两条合起来才是方法："先分归属"本身不是方法，**"在这个片型下，这类现象优先归到执行层"**才是。

倒推时问三句，缺一句就还没成形：

1. 去掉这一步，结果会变成什么样？（说不出变化，说明这步可删）
2. 换一种片型还成立吗？（不成立 → 写成条件句，不写成通则）
3. 失败的时候长什么样？（说不出失败形态，说明只有正例，没有边界）

## 3. 规律还是巧合

三个测试，按成本从低到高：

| 测试 | 通过的样子 | 不通过的样子 |
|---|---|---|
| 换输入 | 换一个题材、换一份素材，这条判断仍然给出可执行的处置 | 只有那一份素材才行得通 |
| 说失效 | 能说出"什么情况下这条反而不对" | 想不出反例，只能说"一般都这样" |
| 可预测 | 拿一个没见过的场景，这句话能预测你会怎么改 | 只能事后解释已经发生的事 |

复现次数只有一次时，不禁止写，但必须标出来：**"一次观察，未复现"**。这条标注会跟着它进库、进 Skill；不标，三个月后没人分得清它是规律还是一次巧合。

## 4. 写成可检验的形式

一个方法的完整形态是四行，缺任一行都不算写完：

```
一句话：我先看观众这一刻该看哪，再看镜头动不动。
可检验特征：画面里已有东西在动（人在走、线在长）时，运镜停住；成片里能看到这段没有叠加运动。
适用条件：实拍或半实拍素材为主；纯代码画的静止画面不适用（那里不动才是缺陷）。
反例：画面静止但需要"活着"的感觉时，停住会被看成卡住——这时该加元素动作，不是加运镜。
```

检验方式：假设明天来一个类似输入，这四行能不能让你在动手前就选出方向？不能，说明它还是描述，不是判据。

## 5. 与 video-library 的分工

同一把尺，两种载体：

| | 库条目 | Skill |
|---|---|---|
| 装多少 | 一条可检验的东西 | 一整套判断：先看什么、分几类、每类怎么处置 |
| 谁读 | 需要时查 | 触发后整套加载 |
| 变化 | 三个月没用就删 | 改动影响所有触发它的会话 |

升级路径：一条库条目被反复读到、并且开始需要"配套的前后顺序"才能用对，才考虑进 Skill。单条事实永远留在库里——把库条目抄成 Skill 正文，只会让每次触发都付一遍查库的成本。

## 6. 切任务边界：一个 Skill 一次可独立验收的判断

一套方法往往覆盖好几个环节。切的时候看"能不能单独验收"，不看"内容像不像一类"：

- 一次只装一个能独立判断的单元：它进来、被触发、给出处置、这件事就算办完了。
- 需要另一个环节的输入才有意义的，不要硬拆成独立 Skill，做成那一个的一节。
- 三件互不相干的事塞进一份 Skill，等于每个触发都付另外两件事的阅读成本；而读不完的部分会被跳过，最后只剩下开头那几段在起作用。

旁证来自外部改造提示词的写法归纳：单次只派发一个可独立验收的单元、先给能力画像再写边界、主上下文不吸收完整代码、重试有上限。同一个成本结构，换到 Skill 上就是"一份 Skill 只承担一个判断单元"。

## 7. 什么时候不该提炼

- 用户只是想把这次的喜好留下来 → 那是 `preferences.md`，一句话就够。
- 这套做法里有一半依赖当前工具的具体版本（某模型锁时长、某脚本参数）→ 只把"查能力"写成方法，具体参数进 `references/` 并标版本与未实测。
- 还没做完、方向还在变 → 现在提炼会把过程中的犹豫写成规则。等这次交付完成再回来看修改记录。

## 8. 产出：一张候选表，不是一份新 Skill

提炼完先给用户看这张表，让他挑哪条值得往下做。不逐条征求同意，也不默认全部保留：

| 候选 | 一句话 | 类型（偏好／方法／一次观察） | 建议去处 |
|---|---|---|---|

挑中的方法再决定：进库条目、进某份 Skill 的一节、还是单独成一份（三问＋"模型本来就会吗"见 SKILL.md §1）。
