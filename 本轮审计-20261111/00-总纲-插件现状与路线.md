### 1.1 三个数字

**渲染器、编辑器、编排器、交付器——装上 DSH 之后一行都不执行。**

### 1.2 它真正能做的，只有五条

`tools/packs.js` 是全插件唯一声明能力的地方：

| capabilityId | 用户得到什么 | 依赖 | 状态 |

| `render-program-visual` | 程序画面渲成成片 | remotion | **只能列、不能执行** |
| `render-quality-check` | 质检渲染、对照 | hyperframes | **只能列、不能执行** |
| `research-lightweight-render` | —— | editly | 自注「调研候选，不能进制作」 |

`kernel.run` **无路由、无调用方**。所以"能力"是五条字符串，不是五个功能。

### 1.3 界面上真实可点的，只有六类，且都不能改画面

**「有没有任何一个按钮能让画面产生变化？」——没有。**

### 1.4 它对模型是零可见的

| 检查 | 结果 |
|---|---|
| `ctx.tools` / `defineTool` / `tools.register` / `ctx.agents` / `ctx.llm` / `ctx.commands` / `ctx.skills` | 全树 **0 命中** |
| Host 半 inject | `['webServer', 'connection']` 两项 |

宿主**支持**（`ctx.tools.register(defineTool({...}))`，描述自动进系统提示词，支持 `{ when }` 按阶段可见）。

所以模型看它=看不见；插件看模型=只看到"人在 UI 里打的字"（`uiState.brief`，`actions.js:327-336`）。

**但模型确实在干活**，方式是把 DSH 当编辑器：读工作区 → 手写 `build-plan.mjs`（28,702 B）→ 跑 `node` → 出 mp4。

### 1.5 防御性代码到底占多少（这一条两个独立审计给出了不同答案，原因值得记）

| 口径 | 行数 | 占比 | 说明 |

**两个数都对，差别在"防御"怎么定义。取中间说法：防御与安全合计约 13–19%，纯工程保证约 12%。**

**我上一轮的判断错了，这里必须修正：防御性代码不是"占了一大半"。**

也就是说：**你写的"记忆与复原"，比你写的"拍摄"还多。**

一句话：**它已经学会了不出错，还没学会拍出来。**

### 1.6 三条真实渲染缺陷（A 从证据里挖出来的，之前没人提）

这些是**已经发生过的**事故，不是理论风险，出处 `实施交接/证据/C16-证据/03-实测缺陷与限制.md`：

| # | 缺陷 | 后果 | 状态 |
|---|---|---|---|
| 1 | FFmpeg 适配器多 xfade 的 offset 基准错 | **成片被截短 52%**（1,464 帧 → 696 帧） | 未修，C16 因此改走 Remotion |
| 2 | 非首场景文字晚出 122 帧 | 字幕与画面错位约 4 秒 | 未修 |
| 3 | `rgba()` 颜色抛错 | 该计划直接渲不出 | 未修 |
| 4 | `fit` / `box` 被渲染层忽略 | **同一对象改属性两次渲染，逐字节相同** | 未修 |

**第 4 条最要命**：它意味着"编辑器"这个产品承诺的核心——改一个属性、画面就变——在 FFmpeg 路径上**从来没有成立过**。

这也是为什么路线乙（Web 场景）不只是"更好看"，它同时是**唯一让"改属性 → 画面变化"成立的路径**：
场景是文件，`params` 进得去，`__seek` 一取帧就看得见。

## 二、能不能优化到达目标

分三层，答案不同。

### 2.1 画面：不能靠优化到达，必须换层——但换层的成本被严重高估了

**为什么优化到不了：**

路线甲（扩 CompositionPlan：加关键帧、transform、mask、blend、排版字段）代价 12–18 人日，
到上限仍是"更精致的 PPT"。原因不是字段不够，是**范式错配**：

| 维度 | 现在 | 证据 |
|---|---|---|
| 推/拉/摇/移 | 不能 | 全库 `zoompan` 命中 0，`camera` 命中 0 |
| 环绕/手持/FOV | 不能 | 无 3D 概念 |
| 遮罩 | 不能 | `mask` `alphamerge` `clipPath` 命中 0 |
| 混合模式 | 不能 | `blend` 命中 0 |
| 字距/行距/竖排 | 不能 | `letter-spacing` 命中 0；`drawtext` 只有 fontfile/textfile/fontsize/fontcolor/x/y/box/alpha/enable |
| 关键帧 | **概念不存在** | `keyframe` 12 次命中全是"编译出来的逐帧数组"，不是可编辑关键帧 |
| 运动术语 | 7 个定义、渲染认 3 个 | `motion.js:29-86` vs 三适配器 |
| 转场 | 3 种（xffmpeg 只用 2 个名字） | `ffmpeg-adapter.js:319` |

**三个"独立"适配器能力完全相同——因为共享同一个对象模型。换适配器不会变好。**

**为什么换层现在变便宜了：**

我原本估计 8–12 人日（写取帧器、写 FFmpeg 收帧、补场景协议）。
**发现那个卡片库之后，这个估计要下调**：`stage.js` 的 `__seek` 接口、确定性、竖版 `data-size` 全都写好了。
你要做的不是"造一个场景系统"，是**"把这个库接进来"**。

吞吐参考（`D-渲染能力.md` 实测，同机 1280×720）：页内 `toDataURL` **11.5 ms/帧** → 1440 帧约 **17 秒**；
慢的从来不是渲染，是 CDP 传 PNG（259 ms/帧）。

### 2.2 模型可见性：能从零加，且这是所有事情的前提

DSH 支持 `ctx.tools.register(defineTool({...}))`。把 19 条路由的读写语义改造成 6–8 个带 schema 的工具，约 **5–8 人日**。

**没有它，模型永远在门外写脚本。** 有了它，模型第一次能"在正确时刻拿到正确信息、做出决定、写回受治理的项目"。

### 2.3 知识：不是"要不要做"，是"已经做好了，接不接"

我上一轮估"92 张卡 ≈ 22 人时"。**这个估算作废。**

因为已经有 **637 张卡 + 128 个成品演示 + 15 个 family + 4 张决策表 + 11 套配方**，MIT。

你要做的不是"写 92 张卡"，是：
1. 把 `index.json` 转成你的检索索引（这是数据搬运，不是创作）
2. 决定这 637 张卡放包内还是包外
3. 把 `decision-tables.md` 的四个维度接进工具描述

**从 22 人时降到约 3–5 人日，而且质量比你自己写的高得多。**

### 2.4 三方案对照（修正后）

| 方案 | 能到的画面 | 工程量 | 保留什么 | 代价 |
|---|---|---|---|---|
| 甲：扩现有引擎 | 更精致的 PPT | 12–18 人日 | 全部 | 到不了目标；滤镜图会变成不可维护单体 |
| **乙：接卡片库 + Web 场景（推荐）** | **128 个成品演示的画面水平** | **6–10 人日** | 时间层 + 治理层 + 工具内核 | 风格偏向"杂志/讲解片"；深度 3D 场景仍需自写 |
| 丙：推倒重来（Blender） | 最高 | 30+ 人日 | 几乎不保留 | 一个人扛不住；GPL 传染；仍需"人"产出资产 |

**推荐乙，而且推荐的理由变了。**
上一轮我说"乙是把断线代码换成真引擎"；现在我可以说得更硬：
**乙是把一个已经做好、MIT、确定性验证过的成品库，接到一个已经做好的时间层上。**
这不是造新东西，是接线。

### 3.6 一张卡应该长什么样（已有实现 vs 你的需要）

`C-方法知识.md` 提出 9 栏格式；**gongnyang 的卡已经覆盖了其中 7 栏**：

## 四、方案：把插件做成目标的样子

### 4.0 架构（五层）

```
┌──────────────────────────────────────────────────────┐
│ ⑤ 知识层   637 张卡 + 128 个演示 + 4 张决策表        │
│            包外，按"能力→症状→约束"三闸检索           │
├──────────────────────────────────────────────────────┤
│ ④ 接口层   ctx.tools：6–8 个带 schema 的工具          │
│            + { when } 阶段门                          │
├──────────────────────────────────────────────────────┤
│ ③ 画面层   Web 场景（stage.js 协议）                   │
│            一个镜头 = 一个可 seek 的网页               │
├──────────────────────────────────────────────────────┤
│ ② 时间层   CompositionPlan（保留，别动）              │
│            整数帧/有理数时长/转场重叠/字幕窗口/音轨     │
├──────────────────────────────────────────────────────┤
│ ① 治理层   项目/版本/锁/恢复（12.4%，刚好）            │
└──────────────────────────────────────────────────────┘
```

### 4.1 六个动作与完成判据

**动作一：把卡片接成画面源（约 6–10 人日，最高优先）**

- 新增对象类型 `web-scene`：`{ sceneId, src, seekMode:'seek'|'clock', readyProbe, params }`
- 取帧器：CDP 控制 + `Runtime.evaluate('__seek(t)')` + 页内 `toDataURL`（不是 `Page.captureScreenshot`）
- 参数注入：改 `stage.js` 之外的 HTML 是脏的；**正确做法是把卡的 HTML 当模板，用 `params` 替换**（`index.json` 的 `params` 就是为此设计的）
- FFmpeg 收帧：`-framerate 30 -i %06d.png` → 叠现有字幕轨 → 编码
- **CompositionPlan 其余部分一行不改**

**完成判据**：能用 `ken-burns` 渲出 10 秒，两次渲染同帧 sha 相同，字幕与之对齐。

**动作二：让模型走进来（约 5–8 人日）**

| 工具 | 何时给 |
|---|---|
| `project.open` / `brief.write` | 一开始 |
| `cards.search`（接 decision-tables 四维） | 决定"这一段怎么拍"之前 |
| `plan.compose` | 有方向之后 |
| `render.preview` | 有计划之后 |
| `evidence.read` | 要确认"这次和上次差在哪" |
| `scene.write` | 要造新世界 |

**完成判据**：模型**不写任何脚本**，从零做出 10 秒画面，全程在锁内、有证据链。

**动作三：补卡片的两个缺口（约 3 人日）**

- 给 128 张有演示的卡补 `slots`（引擎能力槽位）和 `verify`（可复算判据）
- 把 `decision-tables.md` 四维接进 `cards.search` 的描述

**完成判据**：抽 10 张卡，让另一个模型只读卡去实现，≥7 张一次跑通 `verify`。**<5 张回去改格式，不是加卡。**

**动作四：把回路压到 5 分钟（约 3 人日）**

现状是小时级。目标：模型改一版 → 渲 5 秒预览 → 你看 → 再说一句。

**完成判据**：连续 3 次修改，从说话到看到画面 ≤ 5 分钟。

**动作五：两个白送的（约 3 人日）**

- `ffmpeg-adapter.js:319` 放开 xfade 名字表 → **一行，转场从 3 种到 20+**
- `motion.js:181` 让 `rotation` 求值、`:194` 让 `loop` 参与关键帧 → **两行，救活 2 个死术语**
- `motion.js:70-77` 的 `loop-rotate` 直接映射到 gongnyang 的 `camera-orbit` 卡

**动作六：做减法（不着急，但要标记）**

| 砍什么 | 行数 | 为什么 |
|---|---|---|
| 三适配器合成两个 | — | 能力完全相同，维护三份一致性是纯成本 |
| `delivery` 闭包/效果库/项目包往返 | 4,814 | 一个人用，这些是为团队准备的 |
| `editing` 候选/比较/注解全链路 | 5,597 | 改成"一句话+一个对比帧"就够 |
| `orchestration` 方法包/单元/profile | 6,039 | 保留 `craft.js` 的槽位表，其余等真有第二个项目 |

**不必删。但要标记为「冻结，不为它做兼容」**——否则它们会一直收维护税。

### 4.2 顺序的依赖关系

```
动作一（画面）──┐
                ├─→ 动作二（接口）──→ 动作三（补卡）──→ 动作四（回路）
动作五（白送）──┘                                        ↓
                                                   动作六（减法）
```

- 没有动作一，动作三做出来也没人用
- 没有动作二，动作一做好也调不动
- 动作四必须等前三步

**只能做一个，做动作一。**
它是唯一能让你在几天内**亲眼看到**"同一条片，画面从网页录屏拼贴变成有设计的动效"的动作。
而且它用的全是你已经有的东西。

### 4.3 一个反直觉的提醒

那 637 张卡的风格是**杂志感 / 讲解片 / 信息图**，不是你三个 3D 网页的**世界感**。

所以这里有个岔路，必须认清：

| 你要的 | 该用什么 |
|---|---|
| 「画面有设计感、动效可信、信息清楚」 | **637 张卡**（现成，6–10 人日） |
| 「一个活的 3D 世界，镜头在空间里飞」 | **三个 html + user 自写场景**（`D` 路线乙，8–12 人日） |

**这两条不冲突，可以都要**——因为它们的接入层是同一个（`web-scene` + `__seek`）。
`stage.js` 协议和 three.js 的时钟注入，在取帧器眼里是同一种东西。

**但如果只能先做一个，做卡片库。** 理由：它现成、MIT、有 128 个成品证明、有参数、有反模式，
而三个 html 要你自己写场景。

## 五、风险与代价

| 风险 | 影响 | 怎么防 |
|---|---|---|
| **卡片风格不是你要的** | 做出来像"高级 PPT"而不是"电影" | 先渲 3 条样片给你看，你定了再往下做 |
| 卡片的 `index.html` 是演示页面，不是模板 | 直接当渲染源会带上页眉页脚 | `stage.css` 的 `.folio`/`.cap` 可用 `?embed=1` 去掉（实测有效） |
| `params` 替换是字符串级的 | 复杂卡可能替换失败 | 先做 20 张的批量验证，失败率 >10% 就换策略 |
| 跨 GPU 后端像素不同 | 换机器渲出来有细微差别 | 已实测符合现有承诺；验收用"同机两次渲同帧 sha 相同" |
| Chromium 逐帧 4K 成本未知 | 可能 >1 秒/帧 | 先 1080p |
| **许可基线本身有错** | 「严格 MIT」前提要重写 | 动手前先修正；gongnyang 本体是 MIT，但 637 张卡的 `sources` 里有 579 处 `unknown` |
| 减你不舍得删 | 2 万行维护税一直在收 | 不删也行，明确标"冻结" |

**最后一条要说重**：那 637 张卡的 `sources[].license` 分布是——`unknown` 579、MIT 536、Apache-2.0 401、
`MIT + Commons Clause` 68、GSAP 48、Remotion 15、AGPL 1…

**卡本身是 MIT（gongnyang 的 LICENSE 覆盖它自己的表达），但卡里"参考了谁"这件事有 579 处未确认。**
如果你只是自己用，这不影响；如果要分发插件，**必须重新核这一项**。这是你「严格 MIT」基线里真正的坑，
比 Apache/AGPL 那几条更隐蔽。

## 六、什么算「到了」

1. 连续看三遍不难受，第二遍还能看出新东西
2. **关掉字幕也知道在讲什么**
3. 抽任意一帧，脱离上下文仍然像一张海报
4. **关掉声音，节奏还在；关掉画面，声音还成立**
5. 从"我觉得这儿不对"到"看到新版" **≤ 5 分钟**
6. 从你三个网页里随便截 10 秒给别人看，对方会问"这是你做的吗"——成片要达到同样反应

**现在**：离第 6 条最近（网页已经是那水平），离第 5 条最远（回路是小时级）。

**所以真正的进度指标不是画面质量，是回路长度。**

## 七、三个必须你定的问题

### 问题一：你要的是"3D 世界"还是"有设计感的图文"？

- 3D 世界 → 三条 html 自写场景（8–12 人日）
- 有设计感的图文 → **637 张卡**（6–10 人日，现成）
- 两个都要 → 同一接入层，先做卡片库，再加 3D

**判据**：你能接受片子以"信息清楚、动效可信"为主吗？还是必须"看着像一个世界"？

### 问题二：637 张卡里 579 处 `unknown` 许可，你接受吗？

- 自己用 → 接受，但记录来源
- 要分发 → 必须逐卡回查，或只保留 license 明确的那部分（约 1,000 条 MIT/Apache 引用）

### 问题三：那 24,599 行不可达代码，删还是冻结？

- 删 → 立刻轻 2 万行，但以后想用要重写
- 冻结 → 不删，但明确"不为它做兼容、不加测试、不修 bug"

**我的建议：冻结，但把它从"产品的一部分"降级为"遗留库"。** 等你真的需要候选编辑或项目包往返时再解冻。
